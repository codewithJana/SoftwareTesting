What is Selenium?

Definition

Selenium is a free, open-source browser automation suite and the world's most widely used framework for automating web application testing. It controls browsers programmatically using native browser APIs, not injected JavaScript.

Originally created in 2004 by Jason Huggins at ThoughtWorks. Maintained by the non-profit Software Freedom Conservancy.

What CAN you do with Selenium?

  • Automated functional & regression testing of web applications
  • Cross-browser compatibility testing (Chrome, Firefox, Edge, Safari)
  • Full CI/CD pipeline integration — Jenkins, GitHub Actions, Azure DevOps
  • Web scraping and structured data extraction workflows
  • Screenshot & visual regression testing (Applitools, Percy)
  • Mobile web testing via Appium (extends the WebDriver API)
  • Headless browser automation for server-side / cloud execution
  • Integration with AI-powered testing platforms and smart locators

Day 01

The Evolution of Selenium

From a ThoughtWorks internal tool in 2004 to a W3C-standardized global automation framework — Selenium's journey spans two decades of browser automation innovation.

Origins & Foundation (2004 – 2011)
2004 Birth of Selenium (JavaScriptTestRunner) Jason Huggins at ThoughtWorks builds a JavaScript-based test tool to automate web app testing. Core idea: JavaScript controlling the browser from within the page.
2006 WebDriver Created at Google Simon Stewart at Google creates "WebDriver" — bypassing JavaScript limitations by calling native OS-level browser APIs directly for more reliable automation.
2008 Selenium RC 1.0 & Selenium IDE Released Selenium Remote Control (RC) officially released. Selenium IDE (Firefox plugin) launches for record-and-playback test creation for non-programmers.
2009 WebDriver Donated to SeleniumHQ Google donates WebDriver to the Selenium project. Merger of both projects announced — combining the best of Selenium and WebDriver into one framework.
2011 Selenium 2.0 — The Landmark Merger Selenium 2.0 released — WebDriver API merged with Selenium. Deprecated the slow RC architecture. Introduced the clean WebDriver API that became the industry standard.
Standardization & Modern Era (2013 – Present)
2013 Global Dominance Selenium WebDriver becomes the most widely used web automation tool globally. JSON Wire Protocol standardization discussions begin between browser vendors.
2018 W3C WebDriver Standard Published W3C officially publishes WebDriver as a W3C Recommendation — a universal browser automation standard, ensuring cross-vendor consistency across all major browsers.
2021 Selenium 4.0 — Full Modernisation Major release: Full W3C WebDriver compliance, Selenium Grid 4 (complete rewrite), Relative Locators, Chrome DevTools Protocol (CDP) integration, new tab/window APIs.
2022 Selenium 4.6 — Selenium Manager Selenium Manager bundled in — automatically downloads and manages browser drivers. Eliminates the #1 developer pain point: manual ChromeDriver version management.
2023+ BiDi Protocol & AI-era Integration Selenium BiDi (bidirectional WebDriver protocol) integration, enhanced CDP bridging, AI-assisted smart locators, and WebDriver Bidi observability features under active development.

Selenium 4 vs Selenium 3 — Key Differences

Selenium 4 is not just an incremental update — it is a fundamental architectural overhaul driven by the W3C WebDriver standard. Here are the critical differences every automation engineer must know.

Feature / Area Selenium 3 Selenium 4
WebDriver Protocol JSON Wire Protocol — a custom, vendor-specific protocol not officially standardised. W3C WebDriver Protocol — the official, cross-vendor W3C Recommendation standard.
W3C Compliance Partial compliance. Browser vendors implemented their own extensions to the protocol. Full W3C compliance — consistent, predictable behaviour across all browsers.
Grid Architecture Hub-Node model only. Hub is a single point of failure. Limited scalability. Three modes: Standalone, Hub-Node (legacy), and Fully Distributed. Kubernetes-native, Docker-friendly.
Driver Management Manual download required. Developer must match browser version to driver version manually. Selenium Manager (4.6+) — auto-detects browser, downloads the correct driver automatically.
Chrome DevTools Protocol Not supported. Built-in CDP integration — enables network interception, console log capture, geo-mocking, performance metrics.
Relative Locators Not available. Only standard locators (id, name, xpath, css, etc.). 5 new relative locators: above(), below(), near(), toLeftOf(), toRightOf() — locate elements spatially relative to others.
BiDi Protocol Not supported. Experimental BiDi support (Selenium 4.5+) — two-way communication for event listening and network interception.
Tab / Window API Limited — getWindowHandles() only, no built-in new tab method. driver.switchTo().newWindow(WindowType.TAB) and WindowType.WINDOW APIs.
Screenshot Capability Basic window-level screenshot only. Full-page & element-level screenshot support built-in natively.
Browser Authentication No built-in HTTP Basic Auth handling. registerBasicAuth() for handling HTTP Basic Authentication dialogs without extensions.
Internet Explorer Full IE support. IE support dropped — Microsoft officially deprecated IE. IE Mode in Edge available as workaround.
Capabilities API DesiredCapabilities class (now deprecated). Options classes: ChromeOptions, FirefoxOptions, EdgeOptions, SafariOptions — type-safe and IDE-friendly.
Grid Observability No built-in monitoring or metrics. Built-in observability — OpenTelemetry tracing, Prometheus metrics, live session dashboard via Grid UI.

W3C WebDriver Protocol & Browser-Driver Communication

What is the W3C WebDriver Protocol?

  • An HTTP/REST-based communication standard published by the W3C in 2018
  • Commands sent as JSON-encoded HTTP requests (GET / POST / DELETE)
  • Each browser session has a unique session ID used in every endpoint URL
  • Standardised across all browser vendors — no more proprietary quirks
  • Replaces the old, non-standard JSON Wire Protocol used in Selenium 3

Key HTTP Endpoints (Examples)

POST /session
Create a browser session
DELETE /session/{id}
Close / quit session
POST /session/{id}/url
Navigate to URL
POST /session/{id}/element
Find element
POST /.../element/{id}/click
Click element
POST /.../execute/sync
Execute JavaScript

Selenium — Advantages, Limitations & Possibilities

Advantages

  • ✓100% open source — completely free with no licensing cost
  • ✓Multi-language support: Java, Python, C#, JS, Ruby, Kotlin
  • ✓All major browsers: Chrome, Firefox, Edge, Safari
  • ✓Cross-platform: runs on Windows, macOS, and Linux
  • ✓Massive, active community and extensive ecosystem
  • ✓Deep CI/CD integration: Jenkins, GitHub Actions, GitLab CI
  • ✓Integrates with TestNG, JUnit, pytest, NUnit frameworks
  • ✓No vendor lock-in — complete freedom in toolchain choices
  • ✓W3C standard-backed — future-proof and cross-vendor compatible
  • ✓Selenium Grid enables massively parallel cloud execution

Limitations

  • ✕No built-in test runner or assertion library — needs TestNG, JUnit, etc.
  • ✕No native mobile app support — only mobile web via Appium bridge
  • ✕Prone to flaky tests due to timing, dynamic elements, and waits
  • ✕Steeper learning curve vs. Playwright or Cypress for modern apps
  • ✕No built-in reporting — requires Allure, ExtentReports, or custom
  • ✕No native network idle waiting — manual waits required
  • ✕Grid setup overhead for parallel execution in self-hosted environments
  • ✕BiDi / CDP features are still maturing compared to Playwright
  • ✕Slower execution on modern single-page apps vs. Playwright/Cypress
  • ✕Cannot automate Flash/Silverlight (deprecated browser plugins)

From Client-Server to Selenium Architecture

Selenium is built on the same simple idea that powers the entire web — the Client-Server model. Once you understand this, Selenium's architecture makes perfect sense!

The Classic Client-Server Model

How The Web Works
Client (Your Browser)
Chrome, Firefox, Edge — you browsing the web
→ HTTP GET /login.html ← 200 OK (HTML page returned)
Server (Web Application)
Nginx, Apache, Node.js — hosts the web app
1Client sends an HTTP Request to the server (GET, POST, DELETE)
2Server processes the request and sends back an HTTP Response (HTML, JSON)
3The client and server never need to be on the same machine — just a network!
Same idea, different actors

Selenium Uses the Same Pattern!

How Selenium Works
Client (Your Test Script)
Java, Python, C#, JavaScript — your automation code
→ POST /session/{id}/element/click (JSON) ← 200 OK {"value": null} (done!)
Server (Browser Driver)
ChromeDriver, GeckoDriver — listens on localhost:9515
→ CDP / Marionette (internal protocol) ← Element found, action done!
The Real Browser
Chrome, Firefox — performs the actual action
1Test script = Client — sends HTTP commands to the driver server
2Browser driver = Server — receives commands, translates, controls browser
3They talk via W3C WebDriver Protocol = same HTTP/JSON as the web!
This means Selenium tests can run the browser driver on a remote machine (Selenium Grid) just like a web app can have a remote server — it's all just HTTP!
Key Insight for Beginners: Your test script is the "browser" placing orders. ChromeDriver is the "web server" taking orders. They communicate over HTTP + JSON — the same technology that powers every website you visit. Selenium just uses it to automate instead of display pages!
