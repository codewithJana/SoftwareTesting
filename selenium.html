What is Selenium?

Definition

Selenium is a free, open-source browser automation suite and the world's most widely used framework for automating web application testing. It controls browsers programmatically using native browser APIs, not injected JavaScript.

Originally created in 2004 by Jason Huggins at ThoughtWorks. Maintained by the non-profit Software Freedom Conservancy.

  • Automated functional & regression testing of web applications
  • Cross-browser compatibility testing (Chrome, Firefox, Edge, Safari)
  • Full CI/CD pipeline integration — Jenkins, GitHub Actions, Azure DevOps
  • Web scraping and structured data extraction workflows
  • Screenshot & visual regression testing (Applitools, Percy)
  • Mobile web testing via Appium (extends the WebDriver API)
  • Headless browser automation for server-side / cloud execution
  • Integration with AI-powered testing platforms and smart locators

The Evolution of Selenium

From a ThoughtWorks internal tool in 2004 to a W3C-standardized global automation framework — Selenium's journey spans two decades of browser automation innovation.

Origins & Foundation (2004 – 2011)
2004 Birth of Selenium (JavaScriptTestRunner) Jason Huggins at ThoughtWorks builds a JavaScript-based test tool to automate web app testing. Core idea: JavaScript controlling the browser from within the page.
2006 WebDriver Created at Google Simon Stewart at Google creates "WebDriver" — bypassing JavaScript limitations by calling native OS-level browser APIs directly for more reliable automation.
2008 Selenium RC 1.0 & Selenium IDE Released Selenium Remote Control (RC) officially released. Selenium IDE (Firefox plugin) launches for record-and-playback test creation for non-programmers.
2009 WebDriver Donated to SeleniumHQ Google donates WebDriver to the Selenium project. Merger of both projects announced — combining the best of Selenium and WebDriver into one framework.
2011 Selenium 2.0 — The Landmark Merger Selenium 2.0 released — WebDriver API merged with Selenium. Deprecated the slow RC architecture. Introduced the clean WebDriver API that became the industry standard.
Standardization & Modern Era (2013 – Present)
2013 Global Dominance Selenium WebDriver becomes the most widely used web automation tool globally. JSON Wire Protocol standardization discussions begin between browser vendors.
2018 W3C WebDriver Standard Published W3C officially publishes WebDriver as a W3C Recommendation — a universal browser automation standard, ensuring cross-vendor consistency across all major browsers.
2021 Selenium 4.0 — Full Modernisation Major release: Full W3C WebDriver compliance, Selenium Grid 4 (complete rewrite), Relative Locators, Chrome DevTools Protocol (CDP) integration, new tab/window APIs.
2022 Selenium 4.6 — Selenium Manager Selenium Manager bundled in — automatically downloads and manages browser drivers. Eliminates the #1 developer pain point: manual ChromeDriver version management.
2023+ BiDi Protocol & AI-era Integration Selenium BiDi (bidirectional WebDriver protocol) integration, enhanced CDP bridging, AI-assisted smart locators, and WebDriver Bidi observability features under active development.

Selenium 4 vs Selenium 3 — Key Differences

Selenium 4 is not just an incremental update — it is a fundamental architectural overhaul driven by the W3C WebDriver standard. Here are the critical differences every automation engineer must know.

Feature / Area Selenium 3 Selenium 4
WebDriver Protocol JSON Wire Protocol — a custom, vendor-specific protocol not officially standardised. W3C WebDriver Protocol — the official, cross-vendor W3C Recommendation standard.
W3C Compliance Partial compliance. Browser vendors implemented their own extensions to the protocol. Full W3C compliance — consistent, predictable behaviour across all browsers.
Grid Architecture Hub-Node model only. Hub is a single point of failure. Limited scalability. Three modes: Standalone, Hub-Node (legacy), and Fully Distributed. Kubernetes-native, Docker-friendly.
Driver Management Manual download required. Developer must match browser version to driver version manually. Selenium Manager (4.6+) — auto-detects browser, downloads the correct driver automatically.
Chrome DevTools Protocol Not supported. Built-in CDP integration — enables network interception, console log capture, geo-mocking, performance metrics.
Relative Locators Not available. Only standard locators (id, name, xpath, css, etc.). 5 new relative locators: above(), below(), near(), toLeftOf(), toRightOf() — locate elements spatially relative to others.
BiDi Protocol Not supported. Experimental BiDi support (Selenium 4.5+) — two-way communication for event listening and network interception.
Tab / Window API Limited — getWindowHandles() only, no built-in new tab method. driver.switchTo().newWindow(WindowType.TAB) and WindowType.WINDOW APIs.
Screenshot Capability Basic window-level screenshot only. Full-page & element-level screenshot support built-in natively.
Browser Authentication No built-in HTTP Basic Auth handling. registerBasicAuth() for handling HTTP Basic Authentication dialogs without extensions.
Internet Explorer Full IE support. IE support dropped — Microsoft officially deprecated IE. IE Mode in Edge available as workaround.
Capabilities API DesiredCapabilities class (now deprecated). Options classes: ChromeOptions, FirefoxOptions, EdgeOptions, SafariOptions — type-safe and IDE-friendly.
Grid Observability No built-in monitoring or metrics. Built-in observability — OpenTelemetry tracing, Prometheus metrics, live session dashboard via Grid UI.

W3C WebDriver Protocol & Browser-Driver Communication

What is the W3C WebDriver Protocol?

  • An HTTP/REST-based communication standard published by the W3C in 2018
  • Commands sent as JSON-encoded HTTP requests (GET / POST / DELETE)
  • Each browser session has a unique session ID used in every endpoint URL
  • Standardised across all browser vendors — no more proprietary quirks
  • Replaces the old, non-standard JSON Wire Protocol used in Selenium 3

From Client-Server to Selenium Architecture

Selenium is built on the same simple idea that powers the entire web — the Client-Server model. Once you understand this, Selenium's architecture makes perfect sense!

The Classic Client-Server Model

How The Web Works
Client (Your Browser)
Chrome, Firefox, Edge — you browsing the web
→ HTTP GET /login.html ← 200 OK (HTML page returned)
Server (Web Application)
Nginx, Apache, Node.js — hosts the web app
1Client sends an HTTP Request to the server (GET, POST, DELETE)
2Server processes the request and sends back an HTTP Response (HTML, JSON)
3The client and server never need to be on the same machine — just a network!
Same idea, different actors

Selenium Uses the Same Pattern!

How Selenium Works
Client (Your Test Script)
Java, Python, C#, JavaScript — your automation code
→ POST /session/{id}/element/click (JSON) ← 200 OK {"value": null} (done!)
Server (Browser Driver)
ChromeDriver, GeckoDriver — listens on localhost:9515
→ CDP / Marionette (internal protocol) ← Element found, action done!
The Real Browser
Chrome, Firefox — performs the actual action
1Test script = Client — sends HTTP commands to the driver server
2Browser driver = Server — receives commands, translates, controls browser
3They talk via W3C WebDriver Protocol = same HTTP/JSON as the web!
This means Selenium tests can run the browser driver on a remote machine (Selenium Grid) just like a web app can have a remote server — it's all just HTTP!
Key Insight for Beginners: Your test script is the "browser" placing orders. ChromeDriver is the "web server" taking orders. They communicate over HTTP + JSON — the same technology that powers every website you visit. Selenium just uses it to automate instead of display pages!

WebDriver Interface & OOP Concepts

Understanding WebDriver driver = new ChromeDriver() — the most fundamental line in Selenium. This simple statement demonstrates polymorphism, interface implementation, and dependency inversion principles.

The Classic Declaration Explained

WebDriver
driver = new ChromeDriver();
WebDriver (Interface - Reference Type)
An interface defining the contract for browser automation. Contains method signatures like get(), findElement(), quit() — but no implementation.
ChromeDriver (Class - Actual Implementation)
A concrete class that implements the WebDriver interface specifically for Google Chrome. Contains the actual logic to start ChromeDriver.exe, send W3C commands, and communicate via CDP.
driver (Variable Name - Reference)
The variable that holds a reference to the ChromeDriver object. Can call any method defined in the WebDriver interface.

OOP Principles in Action

1️⃣ Polymorphism (Interface-based Programming)
A WebDriver reference can point to any class that implements the interface — ChromeDriver, FirefoxDriver, EdgeDriver. Your test code doesn't care which browser it is — it just calls driver.get(url), and the correct implementation executes.
2️⃣ Abstraction
The WebDriver interface hides complexity. You call driver.findElement(By.id("login")) — you don't need to know that internally ChromeDriver is sending HTTP POST requests, parsing JSON, or invoking CDP commands. All implementation details are abstracted away.
3️⃣ Dependency Inversion Principle
Your test code depends on the WebDriver interface, not the concrete ChromeDriver class. This means you can swap browsers easily without changing test logic — just change new ChromeDriver() to new FirefoxDriver().

Alternative Declaration Options

✅ RECOMMENDED (Interface Reference) 
WebDriver driver = new ChromeDriver();
WebDriver driver = new FirefoxDriver();
WebDriver driver = new EdgeDriver();
Why preferred: Maximum flexibility, polymorphic behavior, easy browser swapping, best practice for cross-browser testing.
⚠️ WORKS BUT NOT RECOMMENDED 
ChromeDriver driver = new ChromeDriver();
Why not preferred: Tightly couples your code to ChromeDriver class. Harder to switch browsers. Violates "program to interface, not implementation" principle. Limits reusability in framework design.
❌ WRONG (Will not compile) 
WebDriver driver = new WebDriver(); // ERROR!
Why it fails: WebDriver is an interface — it has no constructor. You cannot instantiate an interface directly. You must instantiate a concrete implementing class (ChromeDriver, FirefoxDriver, etc.).
🔹 SELENIUM GRID / REMOTE 
WebDriver driver = new RemoteWebDriver(
    new URL("http://grid-hub:4444"),
    new ChromeOptions()
);
Use case: Running tests on remote Selenium Grid nodes, cloud providers (BrowserStack, Sauce Labs), Docker containers, or Kubernetes clusters.

Real-World Justification

Why organizations use interface references:

  • CI/CD Pipeline Flexibility: Same test suite runs on Chrome locally, Firefox in Jenkins, Edge in Azure DevOps — just swap the driver instantiation.
  • Parallel Execution: Selenium Grid requires RemoteWebDriver — easier migration if already using WebDriver interface.
  • Framework Scalability: Base test classes accept WebDriver, not ChromeDriver — supports all browsers without code duplication.
  • Cloud Migration: Switching from local execution to BrowserStack/Sauce Labs just means changing new ChromeDriver() to new RemoteWebDriver(...).

Core Concepts Explained

🔹 What is a Browser Driver?
A browser driver is a standalone executable program that acts as a bridge between your Selenium test code and the actual browser. It runs as an HTTP server listening on localhost (e.g., port 9515 for Chrome). When you call driver.get("https://example.com"), the Selenium library sends an HTTP POST request to the driver, which then translates it into the browser's internal protocol (CDP for Chrome, Marionette for Firefox).
🔹 Why Different Drivers for Different Browsers?
Each browser has its own internal architecture and debugging protocol. Chrome uses CDP, Firefox uses Marionette, Safari uses WebKit Remote Debug. The driver's job is to translate the universal W3C WebDriver HTTP commands into these browser-specific protocols. Think of it like translators — all drivers speak W3C HTTP (input), but each translates to its browser's native language (output).
🔹 Version Compatibility is Critical
The driver version must match the browser version. Chrome 124 needs ChromeDriver 124.x. If they don't match, you'll get errors like session not created: This version of ChromeDriver only supports Chrome version 120. Selenium Manager (4.6+) solves this automatically by detecting your browser version and downloading the matching driver.
🔹 Drivers are Language-Agnostic
ChromeDriver.exe is the same binary whether you're writing tests in Java, Python, C#, or JavaScript. The driver only speaks W3C HTTP — it doesn't care what language your test is written in. The Selenium language binding (Java JAR, Python package, etc.) handles language-specific concerns and sends standard HTTP requests.

Enterprise Best Practices

🏢 Driver Management Strategy
  • Modern (Selenium 4.6+): Use Selenium Manager — zero manual configuration.
  • Legacy (Selenium 3.x): Use WebDriverManager library (Java: io.github.bonigarcia:webdrivermanager) to auto-download drivers.
  • CI/CD Pipelines: Pre-install drivers in Docker images or cache directories to avoid download overhead on every test run.
🏢 Cross-Browser Testing in Organizations
  • Run same test suite on Chrome (80% user base), Firefox (10%), Edge (8%), Safari (2% — Mac users only).
  • Use parameterized tests or TestNG/JUnit @Parameters to switch drivers dynamically.
  • Selenium Grid enables parallel cross-browser execution — 4 browsers × 10 tests = 40 parallel sessions.

Running Tests in Chrome & ChromeDriver.exe

Step-by-step guide to setting up ChromeDriver, understanding its role, and running your first Selenium test in Google Chrome.

Setup Methods (Modern vs Legacy)

OPTION 1: Selenium Manager (Selenium 4.6+) — RECOMMENDED ✅
Zero configuration required! Selenium Manager automatically detects Chrome version, downloads matching ChromeDriver, and sets PATH.
// Step 1: Install Selenium 4.6 or later
// Maven: selenium-java 4.6.0+
// pip install selenium (4.6+)

// Step 2: Just write your test — that's it!
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;

public class FirstTest {
public static void main(String[] args) {
WebDriver driver = new ChromeDriver();
// Selenium Manager handles everything!
driver.get("https://www.google.com");
System.out.println(driver.getTitle());
driver.quit();
}
}
What happens behind the scenes:
1. Detects Chrome version (e.g., 124.0.6367.60)
2. Downloads ChromeDriver 124.x from https://chromedriver.storage.googleapis.com
3. Caches it in ~/.cache/selenium/drivers/chromedriver/
4. Starts ChromeDriver.exe automatically
OPTION 2: Manual Setup (Selenium 3.x or specific control)
You manually download ChromeDriver and configure the system property.
// Step 1: Download ChromeDriver
// Visit: https://chromedriver.chromium.org/downloads
// Download version matching your Chrome browser
// Extract to C:\drivers\chromedriver.exe

// Step 2: Set system property before creating driver
System.setProperty("webdriver.chrome.driver",
"C:\\drivers\\chromedriver.exe");

WebDriver driver = new ChromeDriver();
driver.get("https://www.google.com");
⚠️ Common issues: Version mismatch errors, PATH issues, manual updates when Chrome updates.

What is ChromeDriver.exe?

🔹 Definition
ChromeDriver is a standalone executable file (chromedriver.exe on Windows, chromedriver on Mac/Linux) developed and maintained by the Chromium project. It implements the W3C WebDriver protocol and acts as a server that receives HTTP commands from your Selenium test code and translates them into Chrome DevTools Protocol (CDP) commands that Chrome understands.
🔹 Why is it a Separate File?
Chrome browser and ChromeDriver are updated independently. Chrome is updated frequently (every 4-6 weeks), while your Selenium tests may use a stable version. Separating them allows flexibility — you can update Chrome without breaking your test suite, as long as ChromeDriver versions remain compatible. It also allows the Chromium team to add WebDriver features without modifying the browser itself.
🔹 How Does Selenium Find ChromeDriver?
1. Selenium Manager (4.6+): Auto-downloads and sets PATH internally.
2. System PATH: If chromedriver.exe is in your system PATH environment variable.
3. Explicit Property: System.setProperty("webdriver.chrome.driver", "C:\\path\\chromedriver.exe")
Priority: Explicit property > Selenium Manager > System PATH
🔹 ChromeDriver Startup Process
When you call new ChromeDriver():
1. Selenium starts chromedriver.exe as a background process
2. ChromeDriver starts listening on localhost:9515 (default port)
3. ChromeDriver launches Chrome browser with special automation flags (--remote-debugging-port=12345)
4. Opens a WebSocket connection to Chrome's DevTools Protocol endpoint
5. Returns control to your test script — ready to receive commands

Day 03 · Foundation

What is DOM?

Definition — Document Object Model

DOM stands for Document Object Model. When a browser loads an HTML page, it parses the HTML and creates an in-memory tree-like representation of the entire page. Every HTML tag becomes a node in this tree with parent–child relationships.

The DOM is NOT the HTML source code. It is a live object in the browser's memory that programs (including Selenium) can read and modify at runtime.

Problem Without DOM

  • Selenium cannot read raw HTML strings to find elements
  • Raw HTML has no concept of parent–child–sibling relationships
  • Without DOM, there is no standard API to navigate page structure
  • Dynamically added elements (React/Angular) only exist in the DOM, not the original HTML

How DOM Solves It

  • Browser converts HTML into a structured, navigable tree of objects
  • Every element, attribute, and text becomes an accessible node
  • Selenium queries the DOM using locators — not raw HTML
  • driver.findElement(By.id("login")) traverses the DOM tree

HTML → DOM Tree (Visual)

<html>
  <body>
    <div id="login-form">
      <input id="username" name="user"/>
      <input id="password" name="pwd"/>
      <button id="login-btn">Login</button>
    </div>
  </body>
</html>

DOM Tree:
Document

           └── div#login-form
                ├── input#username  [TEXT node: ""]
                ├── input#password  [TEXT node: ""]
                └── button#login-btn [TEXT node: "Login"]

Enterprise Use Case — Why DOM Matters in Automation

In a banking application login page, the SDET opens DevTools (F12 → Elements tab), inspects the DOM tree to find the id, name, or unique attributes of the input fields. Without DOM knowledge, a tester blindly copies absolute XPaths that break whenever the UI changes. With DOM knowledge, the tester picks stable, semantic attributes — resulting in tests that survive 10+ release cycles.

  • Ancestor: Any node above in the tree hierarchy

Step 4 — CSSOM Built: CSS files are parsed into a CSS Object Model separately
Step 5 — Render Tree: DOM + CSSOM combined to paint the visible page

Day 03 · DOM + Selenium

How Selenium Uses the DOM to Capture WebElements

The Bridge: DOM ↔ Selenium

When you call driver.findElement(By.id("username")), Selenium sends an HTTP POST request to the browser driver. The driver queries the browser's live DOM tree and returns a WebElement reference — an opaque handle to that DOM node. Every subsequent interaction (click, sendKeys, getText) is a DOM operation performed by the browser.

A WebElement is just a reference to a live DOM node. If the DOM changes (page reloads, SPA navigation), the reference becomes stale → StaleElementReferenceException.

Code — findElement & WebElement

// Selenium queries the DOM
WebDriver driver = new ChromeDriver();
driver.get("https://myapp.com/login");

// Selenium → HTTP POST to driver → DOM query
WebElement username =
    driver.findElement(By.id("username"));

// Interact with the DOM node
username.sendKeys("john.doe@company.com");
username.clear();

// Find multiple elements — returns List
List<WebElement> links =
    driver.findElements(By.tagName("a"));
System.out.println("Links: " + links.size());
// Output: Links: 47

// WebElement methods = DOM operations
username.getAttribute("placeholder");
// Output: "Enter your email"
username.isDisplayed();  // true
username.isEnabled();    // true

End-to-End Flow: Test Code → DOM

① You write: driver.findElement(By.id("btn"))
↓
② Selenium binding creates: POST /session/{id}/element {"using":"id","value":"btn"}
↓
③ ChromeDriver receives the W3C HTTP request and translates to CDP
↓
④ Chrome queries its live DOM tree — finds element with id="btn"
↓
⑤ Returns DOM node reference → Java WebElement object

SPA & Dynamic DOM — Enterprise Note

In React/Angular/Vue SPAs, the DOM is updated dynamically after JavaScript executes — elements may not exist when the page first loads. This is why Explicit Waits are mandatory: WebDriverWait + ExpectedConditions.visibilityOfElementLocated() polls the DOM until the element appears, preventing NoSuchElementException in CI/CD pipelines.

Day 03 · Locator 1 of 8

By.id() — The Gold Standard Locator

What & Why

The HTML id attribute must be unique per page (W3C specification). By.id() is the fastest Selenium locator — browsers maintain an internal hash-map of all element IDs, enabling O(1) constant-time lookup. Selenium sends the id value as a query to the DOM and gets back exactly one element.

Always use By.id() as your first choice whenever the element has a stable, non-auto-generated id attribute.

When NOT to Use By.id()

  • Auto-generated IDs: React/Angular create ids like input-4821 that change on every page reload — completely unstable
  • No id attribute: Element simply doesn't have one (use CSS or XPath)
  • Duplicate ids: Poorly coded pages may reuse ids — Selenium always returns the first match, silently hiding bugs

// <input type="text" id="username" name="user"/>
// <input type="password" id="password" name="pwd"/>

        driver.findElement(By.id("username"));
    WebElement password =
        driver.findElement(By.id("password"));
    WebElement loginBtn =
        driver.findElement(By.id("loginBtn"));

By.className() — CSS Class Attribute Locator

What & Why

By.className() locates elements by their CSS class attribute. In HTML, an element can have multiple classes separated by spaces (e.g., class="btn btn-primary active"). With By.className(), provide exactly one class name — Selenium returns all elements containing that class. Use findElements() to get all matches.

Critical Pitfall: By.className("btn btn-primary") throws InvalidSelectorException — spaces in class names are not allowed. Use By.cssSelector(".btn.btn-primary") instead.

Enterprise Use Case — Product Cards Validation

On an e-commerce product listing page, all product cards share class product-card. Using findElements(By.className("product-card")) collects all cards — then loop through them to validate product names, prices, and stock status. Critical for data-driven regression testing across multiple products.

By.tagName() — HTML Tag-based Bulk Locator

What & Why

By.tagName() locates elements by their HTML tag name — a, input, select, table, button, etc. It is almost always used with findElements() to collect all elements of the same type. Rarely used with findElement() since multiple elements share the same tag.

Primary Use Cases: Collect all links (a), all dropdowns (select), all table rows (tr), or all inputs (input) for bulk validation operations.

Enterprise Use Case — Broken Link Detection

A QA team at a major bank must verify no homepage links return HTTP 404/500. By.tagName("a") collects all 87 anchor elements. A for-each loop extracts each href and sends an HTTP HEAD request to validate the response code. This SDET pattern runs in CI/CD before every release, catching broken links in under 2 minutes vs 4 hours of manual testing.

Code Example — Collecting All Links & Dropdowns

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import java.util.List;

public class TagNameDemo {
  public static void main(String[] args) {
    WebDriver driver = new ChromeDriver();
    driver.get("https://company-portal.com");

    // Get ALL anchor tags on the page
    List<WebElement> allLinks =
        driver.findElements(By.tagName("a"));
    System.out.println(
        "Total links: " + allLinks.size());
    // Output: Total links: 47

    // Loop through each link
    for (WebElement link : allLinks) {
      String text = link.getText();
      String href = link.getAttribute("href");
      System.out.println(text + " → " + href);
    }
    // Output:
    // Home → https://company-portal.com/
    // About → https://company-portal.com/about
    // Products → https://company-portal.com/products
    // ... (47 links total)

    // Collect all dropdowns on the page
    List<WebElement> dropdowns =
        driver.findElements(By.tagName("select"));
    System.out.println(
        "Dropdowns: " + dropdowns.size());
    // Output: Dropdowns: 3

    // Collect all table rows (including header)
    List<WebElement> rows =
        driver.findElements(By.tagName("tr"));
    System.out.println(
        "Table rows: " + rows.size());
    // Output: Table rows: 21 (1 header + 20 data rows)

    driver.quit();
  }
}

By.linkText() — Exact Link Text Locator

What & Why

By.linkText() locates anchor elements (<a> tags only) by their exact, complete, visible text. The match is case-sensitive and must be the full text — no partial match. It is simple and readable, making test code highly understandable to non-technical stakeholders.

Important: Only works on <a> elements. Will NOT work on <button>, <span>, or <div> elements even if they look like links.

When to Use By.linkText()

  • Navigation menus with fixed, stable link labels (Home, About Us, Contact)
  • Footer links and breadcrumb navigation
  • When the full link text is unique on the page and won't change between releases
  • Verifying that a specific link exists: try/catch with NoSuchElementException

Code Example — Navigation Menu Testing

// HTML:
// <nav>
//   <a href="/home">Home</a>
//   <a href="/products">Our Products</a>
//   <a href="/about">About Us</a>
//   <a href="/contact">Contact Support</a>
// </nav>

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;

public class LinkTextDemo {
  public static void main(String[] args) {
    WebDriver driver = new ChromeDriver();
    driver.get("https://company.com");

    // Exact match — works perfectly
    driver.findElement(By.linkText("About Us")).click();
    System.out.println(driver.getCurrentUrl());
    // Output: https://company.com/about

    driver.navigate().back();

    // Case-sensitive: "about us" FAILS
    // driver.findElement(By.linkText("about us")); // ❌

    // Partial text FAILS for linkText
    // driver.findElement(By.linkText("Contact")); // ❌

    // Verify link existence (defensive pattern)
    boolean contactExists = false;

      driver.findElement(By.linkText("Contact Support"));

      contactExists = false;

    driver.findElement(
        By.linkText("Our Products")).click();
    System.out.println("URL: " + driver.getCurrentUrl());
    // Output: URL: https://company.com/products

    driver.quit();
  }
}

By.xpath() — Introduction, Absolute vs Relative XPath

What is XPath?

XPath (XML Path Language) is a query language for navigating XML/HTML documents. It traverses the DOM tree in any direction — up to ancestors, down to descendants, or sideways to siblings. XPath is the most powerful but also most complex Selenium locator. It uniquely supports: matching by text content, navigating up to parent elements, and using axes to express complex relationships.

XPath is the only locator that can navigate upward in the DOM (parent, ancestor). CSS can only traverse downward. This is critical for finding elements relative to their labels.

Absolute vs Relative XPath

Absolute /html/body/... Full root-to-element path. Breaks when any ancestor changes. Brittle & fragile. ❌ Never
Relative //tag[@attr=] Searches entire DOM with //. Flexible, readable, and resilient to UI changes. ✅ Always 
// ABSOLUTE — Never use!
/html/body/div[1]/form/div[2]/input[1]

// RELATIVE — Always use //
//input[@id='username']
//input[@type='text' and @name='user']
//button[text()='Login']

Locator Strategy — When to Use Which Locator

Enterprise Locator Priority Order

🥇 1st — By.id(): Fastest O(1) lookup. Use whenever a stable, unique id exists.
🥈 2nd — By.name(): Ideal for form fields with stable name attributes.
🥉 3rd — By.cssSelector(): Complex queries, attribute matching, modern SPAs. Fast & readable.
4th — By.xpath(): When CSS can't handle it — text-based matching, upward navigation, dynamic elements.
5th — By.className(): When a unique, stable single class name exists.
6th — linkText / partialLinkText: Only for stable anchor text in navigation.
❌ Avoid — By.tagName() for single element: Too broad — use only for bulk collection.

Day 03 · Real-World Scenario

Enterprise Use Case — Automated Broken Link Validator

A corporate portal has 200+ navigation links. A broken link (HTTP 404/500) causes poor user experience, SEO penalties, and compliance issues. The SDET automates full link validation using By.tagName("a") + for-each loop + HttpURLConnection.

Problem & Solution

  • Manual testing: Clicking 200+ links takes 3–4 hours per release cycle
  • Links break when backend URLs change, pages are deleted, or typos appear in href
  • Solution: Selenium tagName("a") + Java HttpURLConnection validates all links in <2 minutes
  • Runs automatically in every CI/CD pipeline before deployment

Algorithm Steps

1. Navigate to the page under test
2. Collect ALL anchors with findElements(By.tagName("a"))
3. Loop through each with for-each
4. Extract href attribute from each anchor
5. Send HTTP HEAD request via HttpURLConnection
6. HTTP 200/301 = Valid · HTTP 404/500 = Broken ❌
7. Report summary: broken links count + full URL list

Complete Code — BrokenLinkValidator.java

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import java.net.HttpURLConnection;
import java.net.URL;
import java.util.List;

public class BrokenLinkValidator {
  static WebDriver driver = new ChromeDriver();

  public static void main(String[] args) {
    driver.get("https://company-portal.com");

    // STEP 1: Collect all anchor elements
    List<WebElement> allLinks =
        driver.findElements(By.tagName("a"));
    System.out.println(
        "Total links: " + allLinks.size());
    // Output: Total links: 87

    int brokenCount = 0;

    // STEP 2: Loop through each anchor
    for (WebElement link : allLinks) {
      String href = link.getAttribute("href");

      // Skip null/empty/javascript/fragment hrefs
      if (href == null || href.isEmpty()
          || href.startsWith("#")
          || href.startsWith("javascript")) {
        continue;
      }

      // STEP 3: Validate via HTTP
      int code = getResponseCode(href);

      if (code >= 400) {
        System.out.println(
            "BROKEN [" + code + "]: " + href);
        brokenCount++;
      } else {
        System.out.println(
            "VALID  [" + code + "]: " + href);
      }
    }
    System.out.println("=== SUMMARY ===");
    System.out.println("Broken: " + brokenCount
        + " / " + allLinks.size());
    // Output:
    // VALID  [200]: https://company-portal.com/home
    // BROKEN [404]: https://company-portal.com/old
    // VALID  [200]: https://company-portal.com/about
    // === SUMMARY ===
    // Broken: 1 / 87

    driver.quit();
  }

  static int getResponseCode(String urlStr) {
    try {
      URL url = new URL(urlStr);
      HttpURLConnection conn =
          (HttpURLConnection) url.openConnection();
      conn.setRequestMethod("HEAD");
      conn.connect();
      return conn.getResponseCode();
    } catch (Exception e) {
      return 999; // Connection error
    }
  }
}

findElement & findElements — Introduction

Every Selenium action starts with locating an element. findElement() and findElements() are the two core methods of the WebDriver interface that bridge your test code to the live DOM of the web page.

Why Do We Need These Methods?

In a real web application, every interactive element (button, input, link, dropdown) lives inside the browser's DOM tree. To automate any action — click a button, type in a field, verify text — Selenium must first find that element. findElement() returns a single element reference, while findElements() returns a collection. Without these two methods, automation is impossible.

Problem it solves: Manual testers open a page and visually identify fields. Selenium needs a programmatic way to do the same — these methods are that programmatic bridge.
Both return WebElement(s): A WebElement is a Java object representing a live HTML element in the current page. You can call .click(), .sendKeys(), .getText(), .isSelected() etc. on it.

Side-by-Side Comparison

AspectfindElement()findElements()

If 0 matchesThrows NoSuchElementExceptionReturns empty List (no exception)
If multiple matchReturns the first match in DOM orderReturns all matches in DOM order
Use whenYou expect exactly 1 specific elementYou need to work with multiple elements
Common useLogin button, username field, submitAll links, all checkboxes, table rows

How Selenium Searches the DOM

Step 1: Your Java code calls driver.findElement(By.id("username"))
Step 2: Selenium language binding serialises this into an HTTP POST to ChromeDriver: POST /session/{id}/element with body {"using":"id","value":"username"}
Step 3: ChromeDriver translates the command to CDP and executes a DOM query in Chrome
Step 4: Browser returns a reference ID. Selenium wraps it as a WebElement Java object
Step 5: You now have a live reference — call .click(), .sendKeys(), etc.

⚠️ Key Gotcha: Stale Element Exception

A WebElement reference becomes stale (invalid) if the page reloads, the element is removed or re-rendered after you found it. This throws StaleElementReferenceException.

Fix: Always re-fetch the element after any page navigation or DOM change — do not cache WebElement references across page loads in enterprise frameworks.

A checkbox is an HTML <input type="checkbox"> element that allows users to select or deselect options independently. In enterprise apps, checkboxes appear in settings pages, consent forms, product filters, permission matrices, and user preference screens.

Why Do We Need Special Handling?

Unlike a text field where you just type, a checkbox has a state — checked or unchecked. A naive .click() will toggle its state. isSelected() — Returns true if the checkbox is currently checked, false if unchecked. This is the key method for checkbox handling.
click() — Toggles the checkbox state. Checks it if unchecked; unchecks it if checked.
isEnabled() — Returns true if the checkbox is interactive. A disabled checkbox cannot be clicked and isEnabled() returns false.

Handle Dropdown in Selenium — The Select Class

A dropdown (<select> element) is one of the most common form controls in enterprise applications — country selectors, role pickers, date filters, status dropdowns. Selenium provides the Select class from the org.openqa.selenium.support.ui package specifically for <select> elements.

Why Can't We Just Use click()?

A <select> element is not a simple clickable button. It contains multiple <option> children. You cannot click individual options reliably with just findElement().click() across all browsers and OS combinations. The Select class provides a browser-safe, cross-platform API to interact with native HTML dropdowns.

selectByVisibleText("text") — Selects the option whose visible label matches. Most readable and human-friendly.
selectByValue("value") — Selects the option whose HTML value attribute matches. Reliable even if display text changes.
selectByIndex(int) — Selects by 0-based position in the list. Use when options are dynamic and neither text nor value is predictable.

  <option value="">-- Select Country --</option>
  <option value="IN">India</option>
  <option value="US">United States</option>
  <option value="UK">United Kingdom</option>
  <option value="SG">Singapore</option>
</select>

Complete Java Code — All 3 Selection Methods

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.Select;
import java.util.List;

public class DropdownDemo {
  public static void main(String[] args) {
    WebDriver driver = new ChromeDriver();
    driver.get("https://app.enterprise.com/register");

    // Step 1: Locate the <select> element
    WebElement selectElement =
        driver.findElement(By.id("countrySelect"));

    // Step 2: Wrap it with Select class
    Select countryDrop = new Select(selectElement);

    // ✅ METHOD 1: Select by Visible Text
    countryDrop.selectByVisibleText("India");
    System.out.println("Selected: "
        + countryDrop.getFirstSelectedOption()
                     .getText());
    // Output: Selected: India

    // ✅ METHOD 2: Select by Value attribute
    countryDrop.selectByValue("US");
    System.out.println("Selected: "
        + countryDrop.getFirstSelectedOption()
                     .getText());
    // Output: Selected: United States

    // ✅ METHOD 3: Select by Index (0-based)
    countryDrop.selectByIndex(3);
    System.out.println("Selected: "
        + countryDrop.getFirstSelectedOption()
                     .getText());
    // Output: Selected: United Kingdom

    // ✅ Get all available options
    List<WebElement> allOptions =
        countryDrop.getOptions();
    System.out.println("Total options: "
        + allOptions.size());
    // Output: Total options: 5

    // ✅ Print all option texts
    for (WebElement opt : allOptions) {
      System.out.println("→ " + opt.getText()
          + " [value=" + opt.getAttribute("value")
          + "]");
    }

    // → -- Select Country -- [value=]
    // → India [value=IN]
    // → United States [value=US]
    // → United Kingdom [value=UK]
    // → Singapore [value=SG]

  }
}

  • getOptions(): Returns all <option> elements — use to verify the list contents haven't changed between releases
  • selectByValue() preferred: More resilient than text — display text can be translated to other languages in i18n apps, but the backend value stays constant

  public static void main(String[] args) {
    WebDriver driver = new ChromeDriver();
    driver.get("https://app.enterprise.com/employees");

    // Step 1: Locate the table
    WebElement table =
        driver.findElement(By.id("employeeTable"));

    // Step 2: Get all header columns (th)
    List<WebElement> headers =
        table.findElements(By.tagName("th"));
    System.out.print("Headers: ");
    for (WebElement th : headers) {
      System.out.print("[" + th.getText() + "] ");
    }
    System.out.println();
    // Output: Headers: [Emp ID] [Name] [Department] [Salary] [Action]

    // Step 3: Get all data rows (tr in tbody)
    List<WebElement> rows =
        table.findElements(
            By.xpath(".//tbody/tr"));
    System.out.println(
        "Total rows: " + rows.size());
    // Output: Total rows: 5

    // Step 4: Loop through rows and cells
    for (int i = 0; i < rows.size(); i++) {
      List<WebElement> cells =
          rows.get(i).findElements(
              By.tagName("td"));

      System.out.print("Row " + (i+1) + ": ");
      for (WebElement cell : cells) {
        System.out.print(
            cell.getText() + " | ");
      }
      System.out.println();
    }
    // Output:
    // Row 1: E001 | Alice Johnson | Engineering | 85,000 | Edit |
    // Row 2: E002 | Bob Sharma | QA Automation | 75,000 | Edit |
    // Row 3: E003 | Carol White | Product | 90,000 | Edit |
    // Row 4: E004 | David Lee | DevOps | 80,000 | Edit |
    // Row 5: E005 | Eve Patel | HR | 65,000 | Edit |

    // Step 5: Read a specific cell
    // Row 3, Column 2 (Name) — XPath 1-based
    WebElement specificCell =
        driver.findElement(
            By.xpath(
              "//table[@id='employeeTable']"
              + "//tbody/tr[3]/td[2]"));
    System.out.println("Row 3 Name: "
        + specificCell.getText());
    // Output: Row 3 Name: Carol White

    driver.quit();
  }
}

Code Explanation — Line by Line

table.findElements(By.tagName("th")) — Calls findElements on the table WebElement (not driver), scoping the search to within the table only. Returns all header cells.
By.xpath(".//tbody/tr") — The leading dot (.) means "relative to this element" (the table). Gets only <tr> rows inside <tbody>, excluding the header row.
rows.size() — Dynamically gives the row count. No hard-coding. If backend returns 100 records, this correctly returns 100 — your loop handles them all.
rows.get(i).findElements(By.tagName("td")) — For each row, gets its cells. Nested scoped search — only returns <td> inside that specific <tr>.
cell.getText() — Reads the visible text content of each table cell. Works for text, numbers, and inline links.
XPath tr[3]/td[2]: 1-based indexing in XPath. Row 3 = third data row; td[2] = second column (Name). Used when you need ONE specific cell by position.

Find Row by Cell Value & Click Action

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import java.util.List;

public class WebTableSearchAction {
  public static void main(String[] args) {
    WebDriver driver = new ChromeDriver();
    driver.get("https://hr.enterprise.com/employees");

    String targetEmployee = "Bob Sharma";

    // Get all data rows
    List<WebElement> rows =
        driver.findElements(
            By.xpath(
              "//table[@id='employeeTable']"
              + "//tbody/tr"));

    System.out.println("Searching for: "
        + targetEmployee);
    // Output: Searching for: Bob Sharma

    boolean found = false;

    for (WebElement row : rows) {
      // Read the Name column (2nd td)
      String nameCell =
          row.findElement(
              By.xpath("./td[2]")).getText();

      if (nameCell.equals(targetEmployee)) {
        found = true;
        System.out.println("Found at row: "
            + row.findElement(
                By.xpath("./td[1]")).getText());
        // Output: Found at row: E002

        // Read salary (4th column)
        String salary =
            row.findElement(
                By.xpath("./td[4]")).getText();
        System.out.println(
            targetEmployee + "'s Salary: " + salary);
        // Output: Bob Sharma's Salary: 75,000

        // Click the Edit button in the same row
        row.findElement(
            By.xpath("./td[5]/a")).click();
        System.out.println(
            "Edit clicked for: " + targetEmployee);
        // Output: Edit clicked for: Bob Sharma

        break; // Stop looping — found target
      }
    }

    if (!found) {
      System.out.println(
          "ERROR: Employee not found in table!");
      // Output: (only if not found)
    }

    driver.quit();
  }
}

Code Explanation — Key Patterns

row.findElement(By.xpath("./td[2]")) — The leading dot makes the XPath relative to the current row. td[2] = Name column. This is the key pattern for cell-level navigation within a row.
nameCell.equals(targetEmployee) — String equality check. Selenium's getText() may include leading/trailing spaces — use .trim().equals() in production code for robustness.
row.findElement(By.xpath("./td[5]/a")).click() — Finds and clicks the link inside the 5th column of the same row where the employee was found. This is row-contextual interaction — a critical enterprise pattern.
break statement: Stops the loop after the target row is found and actioned. Without break, the code would continue iterating all remaining rows unnecessarily.
boolean found flag: Clean pattern to detect "element not in table" scenario and print a meaningful error — avoids silent failures in CI reports.

Day 05

Wait Commands — Why Are They Needed?

Modern enterprise web applications are asynchronous — data loads via AJAX, React/Angular re-renders the DOM dynamically, and page transitions involve JavaScript animations. Selenium executes commands at machine speed. Without waits, your test races ahead of the browser and crashes.

The Problem — Race Condition

When you click a button that triggers an AJAX call, the browser starts loading data from the server. Selenium does NOT automatically wait for that AJAX to finish. Your next findElement() fires immediately — and the element may not yet exist.

// ❌ PROBLEM — Test fails intermittently
driver.get("https://crm.enterprise.com/dashboard");
driver.findElement(By.id("search-btn")).click();
// Selenium immediately fires next command ↓
WebElement results =
    driver.findElement(By.id("result-table"));
// ❌ NoSuchElementException — table not loaded yet!
// The AJAX call takes 1-3 seconds to fetch data
Flaky Tests: Without waits, a test passes when the server is fast and fails when it's slow — the #1 cause of unreliable automation suites in enterprise CI/CD pipelines.

Wrong Approach — Thread.sleep()

// ❌ BAD — Hard-coded sleep
driver.findElement(By.id("search-btn")).click();
Thread.sleep(5000); // Always waits 5 seconds
// Problem 1: Wastes 4.5s when data loads in 0.5s
// Problem 2: Still fails when server takes 6s
// Problem 3: 100 tests × 5s = 8+ minutes wasted

A test suite with 500 test cases using Thread.sleep(3000) per test wastes 25 minutes per run doing nothing. In a CI/CD pipeline running every commit, this adds up to hours of wasted compute time daily.

The Solution — 3 Selenium Wait Strategies

1. Implicit Wait
Global timeout applied to every findElement() call in the session. Set once, applies everywhere. Best for legacy apps with consistent load patterns.
2. Explicit Wait (WebDriverWait)
Waits for a specific condition on a specific element — visibility, clickability, text presence, alert, etc. The recommended approach for all modern web apps.
3. Fluent Wait
The most customizable wait. Define polling interval, specific exceptions to ignore, and a custom timeout message. Used for complex async scenarios in enterprise apps.

Common Exceptions Without Waits

NoSuchElementException
Element not yet in DOM when findElement fires
ElementNotInteractableException
Element exists but hidden/disabled (loading state)
StaleElementReferenceException
DOM was re-rendered after you stored the element reference
TimeoutException
Condition not met within the specified wait duration
Day 05 · Wait Strategy 1

Implicit Wait — Global Session Timeout

Implicit Wait is a global setting that instructs WebDriver to poll the DOM for a specified duration before throwing a NoSuchElementException. Set once per session — automatically applied to every findElement() call.

Syntax & Complete Example

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import java.time.Duration;

public class ImplicitWaitDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();

    // SET IMPLICIT WAIT — one line, applies to ALL
    // findElement() calls for the entire session
    driver.manage().timeouts()
        .implicitlyWait(Duration.ofSeconds(10));

    driver.get("https://erp.enterprise.com/orders");

    // No need to add wait before each findElement
    // WebDriver polls for up to 10s automatically

    // Loads in ~2s → driver returns at 2s, not 10s
    driver.findElement(By.id("order-list")).click();

    // Loads in ~1s → driver returns at 1s
    driver.findElement(
        By.id("filter-btn")).click();

    // If element not found in 10s → throws
    // NoSuchElementException (not immediately)

    System.out.println("Page title: "
        + driver.getTitle());
    // Output: Page title: ERP — Order Management

    driver.quit();
  }
}

Code Explanation

driver.manage().timeouts().implicitlyWait(...) — Accesses the session's timeout configuration and sets global polling duration.
Duration.ofSeconds(10) — Java's Duration class (Java 8+). Use this instead of deprecated TimeUnit.SECONDS which was used in Selenium 3.
Polling behaviour: WebDriver checks for the element immediately, then again every 200ms until found or timeout reached. Returns as soon as element is found.
Default value is 0: Without setting implicit wait, a missing element throws NoSuchElementException immediately with no retry.

When to Use / When to Avoid

✓ Use Implicit Wait when:
  • Testing legacy apps with predictable, consistent load times
  • You need a simple, quick setup as a safety net
  • The app does NOT use complex AJAX or SPA frameworks
  • You are building a small, quick prototype test script
✗ Avoid Implicit Wait when:
  • Do NOT mix with Explicit Wait — can cause double-timeout (e.g. 10s + 15s = 20s unexpected)
  • You need to check if element is NOT present (has to wait full timeout)
  • Testing React / Angular / Vue apps where DOM changes dynamically
  • Testing elements that need visibility or clickability checks

How Implicit Wait Works Internally

T = 0msfindElement() fires → element not in DOM yet T = 200msWebDriver polls again → still not found T = 400msPolls again → not found T = 2000msElement appears in DOM → returns immediately OR T = 10000msStill not found → throws NoSuchElementException
⚠️ Important Note: Implicit wait is set per WebDriver session. It applies to every single driver.findElement() call — including those inside Page Object classes, utility methods, and third-party libraries.
Day 05 · Wait Strategy 2 (Recommended)

Explicit Wait — WebDriverWait & ExpectedConditions

Explicit Wait is the most powerful and recommended wait strategy. It waits for a specific condition to be true on a specific element, polling the DOM every 500ms until the condition is met or the timeout expires. It gives precise, per-action control.

Complete Enterprise Example — CRM Search

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.WebDriverWait;
import org.openqa.selenium.support.ui.ExpectedConditions;
import java.time.Duration;

public class ExplicitWaitDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    // Create WebDriverWait — 15s timeout, polls 500ms
    WebDriverWait wait =
        new WebDriverWait(driver, Duration.ofSeconds(15));

    driver.get("https://crm.enterprise.com/contacts");

    // 1. Wait for search box to be CLICKABLE
    WebElement searchBox = wait.until(
        ExpectedConditions.elementToBeClickable(
            By.id("contact-search")));
    searchBox.sendKeys("Acme Corp");

    driver.findElement(By.id("search-btn")).click();

    // 2. Wait for loading spinner to DISAPPEAR
    wait.until(ExpectedConditions
        .invisibilityOfElementLocated(
            By.id("loading-spinner")));

    // 3. Wait for results table to be VISIBLE
    WebElement resultsTable = wait.until(
        ExpectedConditions.visibilityOfElementLocated(
            By.id("results-table")));

    System.out.println("Results loaded: "
        + resultsTable.isDisplayed());
    // Output: Results loaded: true

    // 4. Wait for specific text to appear
    wait.until(
        ExpectedConditions.textToBePresentInElementLocated(
            By.id("result-count"),
            "47 contacts"));
    System.out.println("Status: "
        + driver.findElement(
            By.id("result-count")).getText());
    // Output: Status: 47 contacts found

    driver.quit();
  }
}

Code Explanation — Line by Line

new WebDriverWait(driver, Duration.ofSeconds(15)) — Creates a wait object with 15s max timeout. Default polling: every 500ms. Reusable across multiple wait.until() calls.
wait.until(condition) — Takes an ExpectedCondition<T> and keeps polling until it returns a non-null/non-false value, or throws TimeoutException.
elementToBeClickable(By) — Waits until element is present, visible, and enabled. Most reliable condition before calling .click().
invisibilityOfElementLocated(By) — Waits until spinner/loader is hidden or removed from DOM. Essential after triggering AJAX calls.
visibilityOfElementLocated(By) — Waits until element is present in DOM AND has non-zero dimensions AND is visible (CSS: display≠none, visibility≠hidden).
textToBePresentInElementLocated(By, text) — Checks element's inner text contains the expected string. Perfect for confirming AJAX responses.

The ExpectedConditions class provides 20+ pre-built conditions that cover virtually every real-world synchronization scenario. All are used with WebDriverWait.until().

presenceOfElementLocated(By)
Element exists in DOM (may be hidden). Use for: checking element was injected by JS.
visibilityOfElementLocated(By)
Present AND visible (non-zero size, not hidden). Use for: content panels, modals, data tables.
invisibilityOfElementLocated(By)
Element is hidden or gone from DOM. Use for: loading spinners, overlays disappearing after AJAX.
visibilityOfAllElementsLocatedBy(By)
All matching elements are visible. Use for: verify all 5 menu items rendered in nav bar.

Interactability

elementToBeClickable(By)
Visible AND enabled. Use for: Submit, Save, Delete buttons that are disabled until form is valid.
elementToBeSelected(By)
Checkbox/radio is checked. Use for: verifying pre-selected options in settings pages.
stalenessOf(WebElement)
Old element reference is no longer attached to DOM. Use for: waiting for React re-render, SPA page navigation.
refreshed(ExpectedCondition)
Wraps a condition to handle stale element retries automatically. Use for: dynamic lists that refresh.

attributeContains(By, attr, value)
Element's attribute contains a value. Use for: checking CSS class "active" applied to selected tab.

Day 05 · Wait Strategy 3

Fluent Wait — Customizable Polling & Advanced Control

Fluent Wait is the most configurable wait in Selenium. It extends the WebDriverWait concept but gives you full control over the polling interval, the exceptions to ignore during polling, and a custom timeout message. Use it when standard explicit wait isn't flexible enough.

Complete Fluent Wait Example — Order Status Tracking

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.FluentWait;
import org.openqa.selenium.support.ui.Wait;
import java.time.Duration;
import java.util.NoSuchElementException;

public class FluentWaitDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    driver.get("https://shop.enterprise.com/orders");

    // Configure FluentWait with full control
    Wait<WebDriver> fluentWait =
        new FluentWait<>(driver)
            // Total max time to wait
            .withTimeout(Duration.ofSeconds(30))
            // How often to check the condition
            .pollingEvery(Duration.ofMillis(500))
            // Ignore this exception during polling
            .ignoring(NoSuchElementException.class)
            // Custom message on TimeoutException
            .withMessage(
                "Order status did not change to " +
                "SHIPPED within 30 seconds");

    // Custom condition using a lambda
    // Waits until order status reads "SHIPPED"
    WebElement statusEl = fluentWait.until(
        d -> {
          WebElement el =
              d.findElement(By.id("order-status"));
          String status = el.getText();
          System.out.println("Status: " + status);
          // Return element if condition met, else null
          return status.equals("SHIPPED") ? el : null;
        });

    System.out.println("Final status: "
        + statusEl.getText());
    // Output during polling:
    // Status: PROCESSING
    // Status: PROCESSING
    // Status: PACKING
    // Status: DISPATCHED
    // Status: SHIPPED
    // Final status: SHIPPED

    driver.quit();
  }
}

FluentWait Configuration Deep Dive

.withTimeout(Duration)
Maximum total time before TimeoutException is thrown. Choose based on worst-case scenario response time.
.pollingEvery(Duration)
How often the condition lambda is executed. Default in WebDriverWait is 500ms. For rapid checks use 200ms. For heavy operations use 1000ms.
.ignoring(ExceptionClass)
Silently swallows specified exceptions during each poll cycle. NoSuchElementException is most common. Can chain multiple: .ignoring(NSE.class).ignoring(SERE.class)
.withMessage(String)
Replaces default "Timed out after X seconds" message with descriptive text. Extremely helpful for diagnosing CI/CD failures without digging into screenshots.
Lambda returning null
When your condition is not yet met, return null (or false for Boolean). FluentWait treats null/false as "not satisfied — keep polling".

When to Use FluentWait vs WebDriverWait

Scenario WebDriverWait FluentWait
Standard visibility checks ✓ Overkill
Custom business condition Limited ✓
Custom polling interval 500ms only Any interval
Custom failure message No Yes
Ignore specific exceptions No Yes, multiple

Advanced WebDriver Waits — Enterprise Patterns & Anti-Patterns

Senior SDET engineers build reusable, context-aware wait utilities that handle SPA frameworks, re-renders, and complex state transitions in enterprise applications.

Custom ExpectedCondition — Reusable Wait Utility

import org.openqa.selenium.support.ui.ExpectedCondition;
import java.util.List;

public class CustomWaits {

  // CUSTOM CONDITION 1:
  // Wait until a table has at least N rows loaded
  public static ExpectedCondition<Boolean>
      tableHasMinRows(By tableBy, int minRows) {
    return driver -> {
      List<WebElement> rows =
          driver.findElements(
              By.xpath("//table[@id='" +
                  tableBy.toString() +
                  "']//tbody/tr"));
      return rows.size() >= minRows;
    };
  }

  // CUSTOM CONDITION 2:
  // Wait until an attribute has a specific value
  public static ExpectedCondition<Boolean>
      attributeEquals(By by, String attr,
                      String value) {
    return driver -> {
      try {
        String actual =
            driver.findElement(by)
                  .getAttribute(attr);
        return value.equals(actual);
      } catch (NoSuchElementException e) {
        return false;
      }
    };
  }
}

// USAGE IN A TEST CLASS:
WebDriverWait wait =
    new WebDriverWait(driver, Duration.ofSeconds(20));

// Wait for employee grid to load 15+ rows
wait.until(CustomWaits.tableHasMinRows(
    By.id("employee-grid"), 15));

// Wait for tab CSS class = "active"
wait.until(CustomWaits.attributeEquals(
    By.id("reports-tab"), "class", "tab active"));

System.out.println("Table and tab ready ✓");

Anti-Patterns — What NOT to Do

❌ Mixing Implicit + Explicit
// WRONG — causes double-timeout!
driver.manage().timeouts()
    .implicitlyWait(Duration.ofSeconds(10));
WebDriverWait wait =
    new WebDriverWait(driver, Duration.ofSeconds(15));
// If element missing: waits 10s (implicit)
// THEN WebDriverWait polls: adds up to 20s total!
❌ Thread.sleep() Inside wait.until()
// WRONG — defeats the purpose of the wait
wait.until(d -> {
    Thread.sleep(1000); // Never do this
    return d.findElement(By.id("x")).isDisplayed();
});
❌ Catching TimeoutException silently
// WRONG — hides test failures
try {
    wait.until(EC.visibilityOfElementLocated(...));
} catch (TimeoutException e) {
    // swallowing — test continues even if broken!
}

Enterprise Wait Strategy — Best Practices

  • Use a single WebDriverWait instance per test class or Page Object
  • Set implicitlyWait(0) (default) when using explicit wait — never mix
  • Use elementToBeClickable before every button click in SPAs
  • Use invisibilityOfElementLocated after triggering loading operations
  • Place reusable wait methods in a WaitHelper utility class (Page Object Model)
  • Set timeout per test scenario: quick actions 5s, API-backed actions 20s, batch ops 60s
  • Always add .withMessage() in FluentWait for meaningful CI error logs

Handle Ajax Wait Using JavaScriptExecutor

When an application uses heavy AJAX calls or does NOT expose reliable DOM indicators (no spinner, no status message), you can query the browser's internal JavaScript state directly using JavascriptExecutor to know when all async work is done.

Method 1 — Wait for Page Load (document.readyState)

import org.openqa.selenium.JavascriptExecutor;
import org.openqa.selenium.support.ui.WebDriverWait;
import org.openqa.selenium.support.ui.ExpectedCondition;
import java.time.Duration;

public class AjaxWaitDemo {

  WebDriver driver;
  WebDriverWait wait;

  public AjaxWaitDemo(WebDriver driver) {
    this.driver = driver;
    this.wait =
        new WebDriverWait(driver, Duration.ofSeconds(30));
  }

  // Wait for HTML document to fully load
  // readyState: "loading" → "interactive" → "complete"
  public void waitForPageLoad() {
    wait.until((ExpectedCondition<Boolean>) d -> {
      String readyState = (String)
          ((JavascriptExecutor) d)
              .executeScript(
                  "return document.readyState");
      System.out.println("Page state: " + readyState);
      return "complete".equals(readyState);
    });
    System.out.println("✓ Page fully loaded");
  }

  // Wait for ALL jQuery AJAX calls to finish
  public void waitForJQueryAjax() {
    wait.until((ExpectedCondition<Boolean>) d -> {
      JavascriptExecutor js = (JavascriptExecutor) d;

      // Check if jQuery is even on this page
      Boolean jQueryPresent = (Boolean) js
          .executeScript(
              "return typeof jQuery !== 'undefined'");

      if (!jQueryPresent) return true; // No jQuery - skip

      // jQuery.active == 0 means no active AJAX calls
      Long activeCount = (Long) js
          .executeScript("return jQuery.active");
      System.out.println(
          "Active AJAX calls: " + activeCount);
      return activeCount == 0L;
    });
    System.out.println("✓ All AJAX calls complete");
  }
}

public class SearchTestWithAjaxWait {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();

Window Handle in Selenium — Introduction

In enterprise web applications, actions like clicking "Open Report", "Preview Invoice", or "View Policy" often open a new browser tab or window. Selenium tracks every open window with a unique string called a window handle. Without managing handles, your test gets stuck in the original window.

getWindowHandle() & getWindowHandles()

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import java.util.Set;

public class WindowHandleIntro {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    driver.get("https://portal.enterprise.com");

    // Get handle of the CURRENT (only) window
    String mainHandle = driver.getWindowHandle();
    System.out.println("Main window: " + mainHandle);
    // Output: Main window: CDwindow-4B5E9D7B...

    // Get handles of ALL open windows (as a Set)
    Set<String> allHandles =
        driver.getWindowHandles();
    System.out.println("Open windows: "
        + allHandles.size());
    // Output: Open windows: 1  (only main so far)

    // Action that opens a NEW window/tab
    driver.findElement(
        By.linkText("Open Report")).click();

    // Now there are 2 windows
    Set<String> updatedHandles =
        driver.getWindowHandles();
    System.out.println("After click: "
        + updatedHandles.size() + " windows");
    // Output: After click: 2 windows

    // Selenium 4 — Open a new tab programmatically
    driver.switchTo().newWindow(WindowType.TAB);
    System.out.println("After new tab: "
        + driver.getWindowHandles().size());
    // Output: After new tab: 3 windows

    // Open a new window programmatically
    driver.switchTo().newWindow(WindowType.WINDOW);
    System.out.println("After new window: "
        + driver.getWindowHandles().size());
    // Output: After new window: 4 windows

    driver.quit(); // Closes ALL windows
  }
}

Window Handle Concepts — Deep Dive

What is a Window Handle?
A unique opaque string identifier (e.g., "CDwindow-4B5E9D7B") assigned by WebDriver to each open browser tab or window within a session. Persists for the lifetime of that tab/window.
driver.getWindowHandle() → String
Returns the handle of the currently focused window. Call this BEFORE any action that opens a new window so you can return later.
driver.getWindowHandles() → Set<String>
Returns handles of all open windows in the session. Uses a LinkedHashSet (insertion-ordered) in most drivers — new windows added at the end.
WebDriver does NOT auto-switch
When a new tab opens, WebDriver stays focused on the original window. You must explicitly call driver.switchTo().window(handle) to work with the new tab.
driver.close() vs driver.quit()
driver.close() — Closes only the current window. Must switch back to another handle.
driver.quit() — Closes all windows, ends session, kills driver process.

Day 05 · Window Handle Switching

Window Handle — Switching Between Windows & Enterprise Use Case

The complete pattern for multi-window automation: capture → click → wait → iterate → switch → interact → close → return. This is the standard flow used in every enterprise multi-window test scenario.

Complete Multi-Window Automation — HR Portal

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.*;
import java.time.Duration;
import java.util.Set;

public class WindowSwitchDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    WebDriverWait wait =
        new WebDriverWait(driver, Duration.ofSeconds(15));

    driver.get("https://hrms.enterprise.com/emp");

    // STEP 1: Store the main window handle FIRST
    // (before any click that opens new window)
    String mainWindow = driver.getWindowHandle();
    System.out.println("Main: " + mainWindow);
    // Output: Main: CDwindow-AABB1122...

    // STEP 2: Trigger new window (click opens new tab)
    driver.findElement(
        By.linkText("View Offer Letter")).click();

    // STEP 3: Wait until new window actually opens
    wait.until(d ->
        d.getWindowHandles().size() > 1);

    // STEP 4: Get all handles and find the NEW one
    Set<String> allHandles =
        driver.getWindowHandles();

    String newWindow = null;
    for (String handle : allHandles) {
      if (!handle.equals(mainWindow)) {
        newWindow = handle; // Found the new tab
        break;
      }
    }

    // STEP 5: Switch WebDriver focus to new window
    driver.switchTo().window(newWindow);

    System.out.println("New window title: "
        + driver.getTitle());
    // Output: New window title: Offer Letter - EMP-2024-789

    // STEP 6: Interact with new window content
    WebElement empName = wait.until(
        ExpectedConditions.visibilityOfElementLocated(
            By.id("employee-name")));
    System.out.println("Employee: "
        + empName.getText());
    // Output: Employee: John Doe

    String salary = driver.findElement(
        By.id("ctc-amount")).getText();
    System.out.println("CTC: " + salary);
    // Output: CTC: ₹12,00,000 per annum

    // STEP 7: Close new window and switch BACK
    driver.close(); // close current (offer letter tab)
    driver.switchTo().window(mainWindow);

    System.out.println("Back to: " + driver.getTitle());
    // Output: Back to: HRMS — Employee Management

    driver.quit();
  }
}

Code Explanation — Step by Step

Step 1 — Capture main window
Always store getWindowHandle() BEFORE clicking. This is your "home base" to return to.
Step 3 — Wait for new window
d.getWindowHandles().size() > 1 — waits until the new window is registered with WebDriver before attempting to switch.
Step 4 — Iterate to find new handle
Loop through all handles, skip the main window handle. The remaining handle is the new window.
Step 5 — switchTo().window(handle)
Transfers WebDriver's active context to the new window. All subsequent commands target this window.
Step 7 — close() then switch back
After driver.close(), the current handle is gone. MUST switch back to mainWindow or get NoSuchWindowException.

Common Mistakes & Fixes

Mistake: Not switching back after driver.close()
Fix: Always call driver.switchTo().window(mainWindow) immediately after driver.close()
Mistake: Not waiting for new window to open before getting handles
Fix: Always wait.until(d -> d.getWindowHandles().size() > 1) before iterating handles
Mistake: Assuming handles are ordered (first = main)
Fix: Always use the stored main handle for comparison, not index position

Handling iFrames — Introduction & The Selenium Problem

An <iframe> (inline frame) embeds a separate HTML document inside the current page — often from a different domain. Selenium always starts in the top-level document context. Elements inside an iframe are completely invisible to Selenium until you switch context into the iframe first.

The Problem — Why Selenium Fails Inside iFrames

<!-- Payment Portal HTML Structure -->
<html>
  <body>
    <h1>Complete Your Payment</h1>
    
    <!-- The payment form lives in an iframe -->
    <iframe id="payment-frame"
            src="https://pay.stripe.com/...">

      <!-- These elements are INSIDE the iframe -->
      <!-- Selenium CANNOT see them by default -->
      <input id="card-number" />
      <input id="card-expiry" />
      <input id="card-cvv"    />
      <button id="pay-btn">Pay Now</button>

    </iframe>
    
    <button id="cancel-btn">Cancel</button>
  </body>
</html>
// ❌ FAILS — Selenium is in top-level context

      .sendKeys("4111111111111111");
// Throws: NoSuchElementException:
//   no such element: Unable to locate element
//   {"method":"id","selector":"card-number"}
// 
// Selenium searched the MAIN page's DOM —
// card-number does not exist there!
// It's inside the iframe's separate document.

Why iFrames Create Separate Document Contexts

Browser Security Model: iFrames from different domains (e.g., Stripe's payment widget inside your app) are sandboxed by the browser's same-origin policy. Each iframe has its own window, document, and DOM tree.
Selenium's default context: When you open a page, WebDriver's command context is the top-level document. driver.findElement() searches only this document — it does not traverse into child iframe documents.
Must explicitly switch: Before interacting with iframe content, you must call driver.switchTo().frame() to move WebDriver's context into the iframe's document. After that, all findElement() searches within the iframe.

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.*;
import java.time.Duration;

public class IFrameDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    WebDriverWait wait =
        new WebDriverWait(driver, Duration.ofSeconds(15));

    driver.get("https://shop.enterprise.com/checkout");

    // ─────────────────────────────────────────────
    // METHOD 1: Switch by iframe ID or Name
    // ─────────────────────────────────────────────
    driver.switchTo().frame("payment-frame");
    // WebDriver is now INSIDE the iframe

    driver.findElement(By.id("card-number"))
          .sendKeys("4111111111111111");
    driver.findElement(By.id("card-expiry"))
          .sendKeys("12/27");
    driver.findElement(By.id("card-cvv"))
          .sendKeys("123");

    System.out.println("Card details entered ✓");
    // Output: Card details entered ✓

    // Leave the iframe — back to main page
    driver.switchTo().defaultContent();

    // ─────────────────────────────────────────────
    // METHOD 2: Switch by WebElement (RECOMMENDED)
    // Use with WebDriverWait for reliability
    // ─────────────────────────────────────────────
    WebElement payIframe = wait.until(
        ExpectedConditions
            .presenceOfElementLocated(
                By.id("payment-frame")));

    driver.switchTo().frame(payIframe);
    // Already inside — interact directly

    driver.switchTo().defaultContent(); // back out

    // ─────────────────────────────────────────────
    // METHOD 3: Wait + Switch in one line (Selenium 4)
    // ─────────────────────────────────────────────
    wait.until(ExpectedConditions
        .frameToBeAvailableAndSwitchToIt(
            By.id("payment-frame")));
    // Waits for iframe to load AND switches into it

    driver.findElement(By.id("pay-btn")).click();
    System.out.println("Pay clicked inside iframe ✓");
    // Output: Pay clicked inside iframe ✓

    driver.switchTo().defaultContent();

    // Verify success on main page
    String confirmation = driver.findElement(
        By.id("order-confirmed")).getText();
    System.out.println("Order: " + confirmation);
    // Output: Order: Payment Successful! Order #ORD-789

    // ─────────────────────────────────────────────
    // NESTED IFRAME: iframe inside another iframe
    // e.g., Legacy ERP embedded in modern portal
    // ─────────────────────────────────────────────
    driver.get(
        "https://erp.enterprise.com/reports");

    driver.switchTo().defaultContent(); // Start fresh
    driver.switchTo().frame("outer-frame");
    // Now inside outer iframe

    driver.switchTo().frame("inner-frame");
    // Now inside the nested (inner) iframe

    driver.findElement(By.id("report-input"))
          .sendKeys("Q4-2024");
    System.out.println("Nested input filled ✓");
    // Output: Nested input filled ✓

    // Go up ONE level (to outer iframe)
    driver.switchTo().parentFrame();

    // Go all the way out to main page
    driver.switchTo().defaultContent();

    driver.findElement(
        By.id("submit-report")).click();

    driver.quit();
  }
}

Method Switches To
switchTo().frame("id") iframe by id/name attribute
switchTo().frame(webElement) iframe by WebElement reference (recommended)
switchTo().frame(0) iframe by 0-based index (avoid — fragile)
switchTo().defaultContent() Back to top-level main page document
switchTo().parentFrame() Up one level (for nested iFrames)

Mistake: Trying to switchTo().frame() from inside a nested iframe directly to another frame

Day 06 · Actions Class

Actions Class in Selenium — Foundation

The Actions class in Selenium WebDriver provides a high-level interface for simulating complex user interactions — mouse gestures, keyboard key sequences, and drag-and-drop — that cannot be performed using simple click() or sendKeys() methods alone.

What is the Actions Class?

The Actions class (org.openqa.selenium.interactions.Actions) is Selenium's implementation of the W3C WebDriver Actions API. It allows you to build a chain of actions (a sequence of low-level input events) and execute them all at once using .perform().

Introduced formally in Selenium 2 and fully standardized under W3C WebDriver in Selenium 4, it uses a Builder Pattern — you chain multiple actions together before calling .perform() to execute them atomically.

Package: org.openqa.selenium.interactions.Actions
Pattern: Builder (method chaining)
Final call: .perform() — executes all queued actions
Reset state: ((RemoteWebDriver) driver).resetInputState()

Why is Actions Class Needed? — The Problem

Standard Selenium WebElement methods (click(), sendKeys()) simulate actions at a high level — they simply instruct the browser to fire a click or type event. But many real-world UI interactions require precise mouse movements, button states, and timing that a single click() cannot replicate:

  • Hover menus that only appear when the mouse is physically over an element
  • Context menus that open only on right-click (cannot be triggered by click())
  • Double-click to open/edit an item (two clicks fired as a single atomic event)
  • Drag and drop requires mousedown → move → mouseup in sequence
  • Key combinations like Ctrl+A, Shift+click, Ctrl+C that require holding keys
  • ToolTip verification — tooltips appear only on actual mouse hover events

W3C Actions API — 3 Input Sources

1. Key Input Device
Represents a keyboard. Actions: keyDown(key), keyUp(key), sendKeys(text). Used for typing, Ctrl combos, Tab navigation.
2. Pointer Input Device
Represents a mouse, pen, or touch device. Actions: moveToElement(), click(), contextClick(), doubleClick(), clickAndHold(), dragAndDrop().
3. Wheel Input Device (Selenium 4.2+)
Represents a scroll wheel. Action: scrollToElement(), scrollByAmount() for mouse wheel scroll gestures.

       .keyUp(Keys.SHIFT)
       .perform();

// ✅ Drag and Drop
actions.dragAndDrop(source, target)
       .perform();

// ✅ Drag by Offset (x, y in pixels)

       .perform();

Mouse Hover Action — moveToElement()

A mouse hover (also called "mouseover") occurs when the user physically moves the cursor over an element without clicking it. Many enterprise web UIs have dropdown menus, sub-menus, tooltips, and overlay panels that only appear when the mouse is positioned over a parent element — requiring Selenium's moveToElement().

Right Click (Context Click) in Selenium

A right-click (context click) opens the browser's or application's context menu — a popup menu with contextual actions like Copy, Paste, Open in new tab, or custom app options. Standard Selenium click() fires only a left-click. To simulate a right-click, use Actions.contextClick(element).

Why contextClick() is Needed

  • Data grids (Kendo UI, AG Grid) — right-click row → Edit, Delete, Export
  • File managers — right-click file → Rename, Download, Share
  • Code editors (embedded) — right-click → Copy, Format, Refactor
  • Map components — right-click location → Mark, Navigate
// ❌ FAILS — Left click does nothing

      .click();

// ✅ CORRECT — Right-click opens context menu
Actions actions = new Actions(driver);

    By.id("tableRow-1"));
actions.contextClick(row).perform();

// Now click "Edit" from the context menu
driver.findElement(
    By.xpath("//li[text()='Edit']")).click();

App context menu: Custom HTML/CSS menu rendered inside the webpage. Fully handled by Selenium's contextClick() + standard findElement().

Day 06 · Double Click

Double Click in Selenium — doubleClick()

A double-click fires two rapid left-click events on the same element, triggering dblclick DOM events. Many enterprise UIs use double-click to open a record for editing, expand a tree node, select a word in a text field, or launch a detail view. This cannot be achieved with two sequential click() calls — the timing between clicks must be precise to register as a double-click.

Why Two Separate click() Calls Fail

Two element.click() calls have a large time gap between them — the browser does NOT register this as a dblclick event. The JavaScript event listener on dblclick is never fired.

// ❌ WRONG — Two separate clicks ≠ dblclick
driver.findElement(By.id("emp-row-1")).click();
driver.findElement(By.id("emp-row-1")).click();
// Does NOT fire ondblclick event!

// ✅ CORRECT — Actions.doubleClick()
Actions actions = new Actions(driver);
WebElement row = driver.findElement(
    By.id("emp-row-1"));
actions.doubleClick(row).perform();
// Fires: mousedown → mouseup → click
//      → mousedown → mouseup → click
//      → dblclick  (all in one atomic action)
The doubleClick() method fires: mousedown → mouseup → click → mousedown → mouseup → click → dblclick — in one atomic sequence at the correct system timing.

Enterprise Use Cases for Double-Click

  • ERP data grids — double-click a row to open inline edit mode
  • File/Document managers — double-click to open a document or folder
  • Calendar applications — double-click a time slot to create new event
  • Tree view widgets — double-click a node to expand/collapse
  • Canvas/Diagram editors — double-click shape to open property editor

Day 06 · Drag and Drop

Drag and Drop in Selenium — Introduction

Drag and Drop is a compound mouse gesture: the user presses and holds the left mouse button on a source element, moves the cursor to a target location, and releases the button. It is used extensively in enterprise UIs — Kanban boards, workflow designers, file uploaders, dashboard widget reordering, and form builders.

How Drag and Drop Works — Event Sequence

A drag-and-drop operation fires a specific sequence of DOM events on the browser:

1. mousedown on source element
2. mousemove (one or more) toward target
3. mouseenter on target element
4. mouseover on target element
5. mouseup on target element

Selenium's dragAndDrop() fires all these events atomically — it performs clickAndHold on source, moves to target, then release on target.

// ❌ Wrong — manual click/move won't work
driver.findElement(By.id("src")).click();

// ✅ Method 1: dragAndDrop(source, target)
Actions actions = new Actions(driver);
WebElement source = driver.findElement(
    By.id("draggable"));
WebElement target = driver.findElement(
    By.id("droppable"));
actions.dragAndDrop(source, target).perform();

Enterprise Use Cases

  • Jira / Azure DevOps — drag a story card from "To Do" to "In Progress"
  • Dashboard builders — reorder chart widgets by dragging
  • File upload zones — drag files into upload dropzone
  • Visual workflow editor — drag approval nodes to a canvas
  • E-commerce sort — reorder product images by drag

Day 06 · Drag and Drop Advanced

Drag and Drop — dragAndDropBy() & Manual Pattern

When the drop target is not a fixed element (e.g., a resizable splitter, a slider, or a canvas) you need dragAndDropBy() which moves the element by a given pixel offset (x, y). For cases where dragAndDrop() fails due to JavaScript-heavy libraries (React DnD, Sortable.js), use the manual clickAndHold → moveToElement → release pattern.

dragAndDropBy() — Pixel Offset

// METHOD: dragAndDropBy(element, xOffset, yOffset)
// Moves element by (x, y) pixels from its
// current center position.

Actions actions = new Actions(driver);
WebElement draggable = driver.findElement(
    By.id("resizable-handle"));

// Move 200px to the right, 0px vertically
actions.dragAndDropBy(draggable, 200, 0)
       .perform();

// ────────────────────────────────────────
// Calculating offset using getRect():
WebElement source = driver.findElement(
    By.id("draggable"));
WebElement target = driver.findElement(
    By.id("droppable"));

Rectangle srcRect = source.getRect();
Rectangle tgtRect = target.getRect();

int xOff = tgtRect.getX() - srcRect.getX();
int yOff = tgtRect.getY() - srcRect.getY();

actions.dragAndDropBy(source, xOff, yOff)
       .perform();
System.out.println("Dropped at target position");
// Output: Dropped at target position
getRect() returns the element's x, y position and width, height as a Rectangle object. Using the difference of x,y coordinates ensures precise placement.

Manual Pattern — For JS-Heavy Drag Libraries

Libraries like React DnD, Sortable.js, Angular CDK DragDrop sometimes don't respond to Selenium's dragAndDrop() because they listen to custom pointer events. The manual step-by-step pattern gives finer control:

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.interactions.Actions;
import org.openqa.selenium.support.ui.*;
import java.time.Duration;

public class DragDropManualDemo {
  public static void main(String[] args) {

    WebDriver driver = new ChromeDriver();
    WebDriverWait wait = new WebDriverWait(
        driver, Duration.ofSeconds(10));

    driver.get(
        "https://dashboard.enterprise.com");
    driver.manage().window().maximize();

    Actions actions = new Actions(driver);

    WebElement widget = wait.until(
        ExpectedConditions.presenceOfElementLocated(
            By.id("sales-chart-widget")));

    WebElement dropZone = driver.findElement(
        By.id("dashboard-slot-3"));

    System.out.println("Starting manual drag...");

    // STEP 1: Press and hold on source widget
    actions.clickAndHold(widget).perform();
    System.out.println(
        "Step 1: Click and hold on widget");
    // Output: Step 1: Click and hold on widget

    // STEP 2: Add pause — allows drag to register
    actions.pause(Duration.ofMillis(500))
           .perform();

    // STEP 3: Move gradually toward target
    actions.moveToElement(dropZone).perform();
    System.out.println(
        "Step 2: Moved to drop zone");
    // Output: Step 2: Moved to drop zone

    // STEP 4: Pause to allow drop-target to detect
    actions.pause(Duration.ofMillis(500))
           .perform();

    // STEP 5: Release mouse on target
    actions.release(dropZone).perform();
    System.out.println(
        "Step 3: Released — widget dropped!");
    // Output: Step 3: Released — widget dropped!

    // STEP 6: Verify widget moved to slot 3
    WebElement slot3Widget = wait.until(
        ExpectedConditions.presenceOfElementLocated(
            By.cssSelector(
              "#dashboard-slot-3 "
            + "#sales-chart-widget")));
    System.out.println("Widget in slot 3: "
        + slot3Widget.isDisplayed());
    // Output: Widget in slot 3: true

    driver.quit();
  }
}

Day 06 · Keyboard Events

Keyboard Events in Selenium Actions Class

The Actions keyboard API allows simulating any keyboard input including modifier keys (Ctrl, Shift, Alt), function keys (F1–F12), navigation keys (Tab, Enter, Escape), and key combinations. This is essential for testing keyboard-accessible enterprise UIs, form navigation, and shortcuts.

Why Keyboard Actions in Actions Class?

While WebElement.sendKeys() types text into a focused element, it cannot:

  • Hold a key down while performing other actions (e.g., Shift+click)
  • Fire key events globally (not on a specific element)
  • Mix keyboard and mouse actions in a single atomic sequence
  • Simulate shortcut combos like Ctrl+A, Ctrl+C, Ctrl+V
keyDown(key) — Presses and holds the key. The key stays depressed until keyUp() is called. Used for modifier keys like SHIFT, CTRL, ALT.
keyUp(key) — Releases a previously held key. Always pair every keyDown() with a keyUp() to prevent stuck key state.
sendKeys(text) — Convenience method combining keyDown + keyUp for each character. Supports Keys enum constants.

Keys.SHIFT — Shift
Keys.ALT — Alt
Keys.TAB — Tab
Keys.ENTER — Enter
Keys.ESCAPE — Escape
Keys.BACK_SPACE — Backspace
Keys.DELETE — Delete
Keys.ARROW_UP — ↑
Keys.ARROW_DOWN — ↓
Keys.HOME / Keys.END

           .keyDown(Keys.SHIFT)

           .sendKeys("a")   // Ctrl+A
           .keyUp(Keys.CONTROL)
           .perform();
    System.out.println("All text selected");
    // Output: All text selected

    // ─────────────────────────────────────
    // EXAMPLE 3: Delete selected text
    // ─────────────────────────────────────

        + noteField.getAttribute("value") + "'");

Day 07 — Robot Class

What is Robot Class?

Definition

java.awt.Robot is a core Java class (part of AWT) that generates native system-level input events — mouse moves, clicks, and keyboard presses — at the OS level, not browser level.

  • No Maven dependency needed — it's part of core Java
  • Works independently of any browser or Selenium
  • Operates at actual screen pixel coordinates

Why Do We Need It?

Selenium WebDriver cannot interact with native OS dialogs. Robot bridges this gap:

  • File Upload / Download dialogs
  • Windows Authentication popups
  • Print dialogs
  • CAPTCHA / screen interactions
  • Taking screenshots at pixel level

    robot.keyRelease(KeyEvent.VK_ENTER);

Selenium Headless Browser Testing

What is Headless Testing?

Running browser tests without a visible GUI. The browser engine runs in memory — no window is displayed. Ideal for:

  • CI/CD pipelines (Jenkins, GitHub Actions, GitLab CI)
  • Docker containers (no display server)
  • Faster parallel test execution (~2× speed gain)
  • Server environments without a desktop

import org.openqa.selenium.chrome.*;

TestNG Introduction — What Is It & Why Do We Need It?

TestNG (Test Next Generation) is an open-source testing framework for Java, inspired by JUnit and NUnit. Created by Cédric Beust at Google in 2004 to overcome JUnit's limitations — especially for enterprise Selenium WebDriver automation suites.

The Problem — What Was Missing in JUnit?

Before TestNG, Java teams used JUnit. For enterprise Selenium automation, JUnit had critical limitations:

  • No test grouping: Couldn't selectively run "smoke" or "regression" tests from the same class
  • No test dependencies: No way to say "run loginTest BEFORE dashboardTest and skip dashboard if login fails"
  • No data-driven testing: Running same test with multiple datasets required complex workarounds
  • No parallel execution: Tests ran sequentially, making large CI/CD suites painfully slow
  • No suite XML config: No external way to define complex test execution plans without code changes
  • No @BeforeSuite/@AfterSuite: No lifecycle hooks at the suite level for DB connections, etc.

The Solution — What TestNG Provides

  • Annotations-driven: No class inheritance — just annotate any public method
  • Flexible grouping: Tag tests as "smoke", "regression", "login" — run selectively
  • Test dependencies: dependsOnMethods / dependsOnGroups with automatic skip on failure
  • @DataProvider: Run the same test with 100 data sets in a single method
  • Parallel execution: Run tests in parallel (methods / classes / suites / instances)
  • testng.xml: Define entire execution plan externally — no code changes for different runs
  • Rich HTML reports: Auto-generated detailed test execution reports
  • Priority control: Control execution order with the priority attribute

TestNG Annotations — Complete Overview & Lifecycle

Annotations are the heart of TestNG. They tell TestNG when and how to run your code — before the suite starts, before each test class, or after each method. No class inheritance needed; just annotate any public method with the right annotation.

All TestNG Annotations — Execution Hierarchy (Outer → Inner)

@BeforeSuite — Runs ONCE before the entire suite begins
@AfterSuite — Runs ONCE after the entire suite finishes
@BeforeTest — Runs before each <test> tag in testng.xml
@AfterTest — Runs after each <test> tag in testng.xml
@BeforeGroups — Runs before the 1st method of named groups
@AfterGroups — Runs after the last method of named groups
@BeforeClass — Runs ONCE before the first @Test in this class
@AfterClass — Runs ONCE after all @Test methods in this class
@BeforeMethod — Runs before EVERY @Test method
@AfterMethod — Runs after EVERY @Test method
@Test — Marks a method as a Test Case (the actual test!)
@DataProvider — Supplies data for parameterized tests
@Parameters — Passes XML parameters to tests
@Listeners — Adds test listeners (reporting / logging)

TestNG Test Suite — testng.xml Structure & Configuration

A TestNG Test Suite is a collection of tests defined in the XML file testng.xml — the control center of TestNG. It defines WHAT to run, HOW to run (parallel/sequential), WHICH groups to include/exclude, and WITH WHAT parameters — all without touching Java code.

Why testng.xml Is Needed

Problem: 200 test classes. Run only "login module" tests.
Solution: Define a <test> block with only those classes in testng.xml
Problem: Run all "smoke" group tests across all classes.
Solution: <include name="smoke"/> in testng.xml — no code change
Problem: CI needs env params (URL, browser, credentials).
Solution: <parameter name="browser" value="chrome"/>
Problem: Tests are slow — need parallel execution.
Solution: parallel="methods" thread-count="4" on <suite>

testng.xml Hierarchy

<suite> — Top-level container (entire test run)
<test> — A logical group of test classes
<classes> — Container for Java class definitions
<class> — A specific Java test class (full qualified name)
<methods> — Specific methods to include/exclude

Thread-Safe Selenium — ThreadLocal<WebDriver> Pattern

import org.testng.annotations.*;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.firefox.FirefoxDriver;

// Thread-safe WebDriver — ESSENTIAL for parallel tests!
public class BaseTest {

    // ThreadLocal: each thread gets its own WebDriver
    // Without this: threads share one driver → tests fail!
    private static ThreadLocal<WebDriver>
        driver = new ThreadLocal<>();

    @Parameters({"browser"})
    @BeforeMethod
    public void setUp(String browser) {
        WebDriver d;
        if ("firefox".equalsIgnoreCase(browser)) {
            d = new FirefoxDriver();
        } else {
            d = new ChromeDriver(); // default chrome
        }
        driver.set(d);  // Store driver for THIS thread
        getDriver().manage().window().maximize();
        System.out.println("Started: " + browser +
            " [Thread: " +
            Thread.currentThread().getId() + "]");
    }

    // Static accessor — any test class can call this
    public static WebDriver getDriver() {
        return driver.get();  // returns THIS thread's driver
    }

    @AfterMethod
    public void tearDown() {
        if (getDriver() != null) {
            getDriver().quit();
            driver.remove(); // clean up ThreadLocal
        }
    }
}

// Test class extends BaseTest
public class LoginTest extends BaseTest {

    @Test(groups = "smoke")
    public void testLogin() {
        // Thread 1 → Chrome driver
        // Thread 2 → Firefox driver (simultaneously!)
        getDriver().get("https://app.enterprise.com");
        System.out.println("Testing login...");
    }
}
// Output (parallel="tests", thread-count=2):
// Started: chrome [Thread: 12]
// Started: firefox [Thread: 13]
// Testing login... (from Chrome)
// Testing login... (from Firefox - same time!)
Enterprise Rule: Always use ThreadLocal<WebDriver> for parallel Selenium. Never use a shared static WebDriver — threads will interfere causing flaky test results.

TestNG Dependent Tests — Controlling Execution Order & Skip on Failure

TestNG allows declaring dependencies between test methods or groups. This solves a real problem: You cannot test "checkout" if "login" failed — you won't be logged in! TestNG automatically marks dependent tests as SKIP when their dependency fails.

Why Dependent Tests Are Needed

❌ Problem Without Dependencies:
Login FAILS → Dashboard runs anyway → "Not logged in" error → Cart test runs → "Session expired" → 50 tests FAIL — but root cause is just 1 broken login!
✅ Solution With Dependencies:
Login FAILS → All dependent tests auto-SKIP → Report shows: 1 FAIL, 49 SKIPs → Root cause is immediately obvious!

dependsOnMethods — Method Dependencies

import org.testng.annotations.Test;

public class ECommerceFlowTest {

  @Test(priority = 1)
  public void testLogin() {
    System.out.println("✅ Logged in");
    // if FAILS → ALL below are SKIPPED
  }

  @Test(priority = 2,
        dependsOnMethods = {"testLogin"})
  public void testSearch() {
    System.out.println("✅ Searched product");
    // SKIPPED if testLogin FAILED
  }

  @Test(priority = 3,
        dependsOnMethods = {"testSearch"})
  public void testAddToCart() {
    System.out.println("✅ Added to cart");
  }

  @Test(priority = 4,
        dependsOnMethods = {"testAddToCart"})
  public void testCheckout() {
    System.out.println("✅ Order placed");
  }
}
// All Pass:
// PASSED: testLogin → testSearch →
//         testAddToCart → testCheckout
// Tests: 4, Failures: 0, Skips: 0

// If testLogin FAILS:
// FAILED:  testLogin
// SKIPPED: testSearch
// SKIPPED: testAddToCart
// SKIPPED: testCheckout
// Tests: 1, Failures: 1, Skips: 3

TestNG Asserts — Foundation of Test Validation

An Assert is the mechanism that determines whether a test passes or fails. Without assertions, every test always passes — even when the application is completely broken. TestNG provides the org.testng.Assert class with powerful assertion methods used in every enterprise Selenium project.

The Problem — Why Asserts Are Mandatory

Imagine testing a login page. Without assert:

@Test
public void testLogin() {
    driver.findElement(By.id("username")).sendKeys("admin");
    driver.findElement(By.id("password")).sendKeys("admin@123");
    driver.findElement(By.id("loginBtn")).click();
    // NO ASSERT — test ALWAYS PASSES ❌
    // Even if the login fails in the app!
}
Result: This test gives a false green — it tells you everything is fine when the app might be completely broken. This defeats the entire purpose of automation.

The Solution — Assert Validates the Outcome

@Test
public void testLogin() {
    driver.findElement(By.id("username")).sendKeys("admin");
    driver.findElement(By.id("password")).sendKeys("admin@123");
    driver.findElement(By.id("loginBtn")).click();

    // Get actual page title after login
    String actualTitle = driver.getTitle();

    // Assert: expected vs actual
    Assert.assertEquals(actualTitle,
        "Dashboard | MyApp",
        "Login failed — expected Dashboard page!");
    // ✅ PASS if title matches
    // ❌ FAIL with message if title doesn't match
}

All TestNG Assert Methods — Quick Reference

Method When It PASSES
assertEquals(actual, expected) actual equals expected
assertNotEquals(a, b) a does NOT equal b
assertTrue(condition) condition is true
assertFalse(condition) condition is false
assertNull(object) object is null
assertNotNull(object) object is NOT null
assertSame(a, b) a and b reference same object
assertNotSame(a, b) a and b are different objects

TestNG Soft Assertions — Accumulate All Failures

With Hard Asserts, a test stops at the first failure — you never know how many issues exist. Soft Assertions (SoftAssert) collect all failures across the test and report them together at the end using assertAll(). This is critical for UI form validation testing in enterprise applications.

Problem — Hard Assert Stops at First Failure

// Hard Assert — Stops at FIRST failure
@Test
public void validateUserProfilePage() {
    // Assume: Name is wrong, Email is wrong,
    // Phone is wrong

    // Test STOPS here — name mismatch
    Assert.assertEquals(
        driver.findElement(By.id("name")).getText(),
        "John Doe");  // ❌ STOPS — reports 1 error

    // These are NEVER reached!
    Assert.assertEquals(
        driver.findElement(By.id("email")).getText(),
        "john@company.com");  // Never executed

    Assert.assertEquals(
        driver.findElement(By.id("phone")).getText(),
        "+1-800-555-0100"); // Never executed
}
// Result: You only know about 1 failure.
// Remaining 2 bugs are HIDDEN!
Problem: With Hard Assert, each test run reveals only ONE bug at a time. For a form with 10 fields, you'd need 10 test runs to discover all issues — extremely inefficient.

Solution — SoftAssert Captures ALL Failures

import org.testng.asserts.SoftAssert;

@Test
public void validateUserProfilePage() {
    SoftAssert sa = new SoftAssert();
    // Create instance inside the @Test method!

    sa.assertEquals(
        driver.findElement(By.id("name")).getText(),
        "John Doe",
        "Name field mismatch");
    // ❌ Fails — but continues execution!

    sa.assertEquals(
        driver.findElement(By.id("email")).getText(),
        "john@company.com",
        "Email field mismatch");
    // ❌ Fails — still continues!

    sa.assertEquals(
        driver.findElement(By.id("phone")).getText(),
        "+1-800-555-0100",
        "Phone field mismatch");
    // ❌ Fails — still continues!

    sa.assertAll();
    // NOW reports ALL 3 failures together
}

2) Email field mismatch: expected [john@company.com] but found [john@corp.com]

TestNG Test Priority — Controlling Execution Order

By default, TestNG runs @Test methods in alphabetical order — which is rarely what you want in a real test suite. The priority attribute lets you define the exact sequence. This is essential when tests depend on each other — you must log in before testing the dashboard, create a record before editing it.

Problem — Default Alphabetical Ordering Breaks Tests

// Without priority — runs alphabetically: ❌
public class ECommerceFlow {

    @Test
    public void addToCart() { ... }     // Runs 1st

    @Test
    public void checkout() { ... }      // Runs 2nd

    @Test
    public void login() { ... }         // Runs 3rd

    @Test
    public void placeOrder() { ... }    // Runs 4th

    @Test
    public void verifyOrderEmail() { }  // Runs 5th
}
// TestNG orders by: addToCart → checkout → login
// → placeOrder → verifyOrderEmail
// Problem: checkout runs BEFORE login! ❌
// Tests will fail because user isn't logged in.
Root Cause: TestNG does not guarantee method declaration order. Alphabetical ordering results in logically incorrect execution flow. Business flows (login → cart → checkout → order) must be enforced explicitly.

Solution — priority Attribute Enforces Sequence

// With priority — runs in defined order: ✅
public class ECommerceFlow {

    @Test(priority = 1)
    public void login() {
        // Always runs FIRST
        driver.get("https://shop.company.com/login");
        driver.findElement(By.id("user"))
              .sendKeys("tester@company.com");
        driver.findElement(By.id("pass"))
              .sendKeys("Test@1234");
        driver.findElement(By.id("loginBtn")).click();
        Assert.assertEquals(driver.getTitle(),
            "Home | ShopApp", "Login failed");
        System.out.println("✅ Step 1: Logged in");
    }

    @Test(priority = 2)
    public void addToCart() {
        // Runs AFTER login
        driver.findElement(By.id("laptop-add")).click();
        Assert.assertEquals(
            driver.findElement(By.id("cart-qty"))
                  .getText(), "1");
        System.out.println("✅ Step 2: Item added");
    }

    @Test(priority = 3)
    public void checkout() {
        driver.findElement(By.id("checkoutBtn")).click();
        Assert.assertTrue(
            driver.getCurrentUrl().contains("checkout"));
        System.out.println("✅ Step 3: Checkout page");
    }

    @Test(priority = 4)
    public void placeOrder() {
        driver.findElement(By.id("confirmBtn")).click();
        String msg = driver.findElement(
            By.id("successMsg")).getText();
        Assert.assertTrue(msg.contains("Order Placed"));
        System.out.println("✅ Step 4: Order placed");

TestNG Parameters — Externalizing Test Configuration

Hardcoding test values (URLs, browser names, credentials, environments) in Java code is an anti-pattern that makes maintenance a nightmare. @Parameters lets you define values externally in testng.xml and inject them into test methods at runtime — enabling the same test code to run on different environments, browsers, and datasets without code changes.

Problem — Hardcoded Values Break Flexibility

// ❌ Hardcoded — Cannot change env without code change
@BeforeClass
public void setUp() {
    driver = new ChromeDriver(); // Hardcoded Chrome!
}

@Test
public void testLogin() {
    driver.get("https://UAT.myapp.com/login"); // Hardcoded!

          .sendKeys("admin123"); // Hardcoded!
}
// To run on PROD or Firefox?
// You must EDIT and RECOMPILE Java code every time.
// This is NOT maintainable for 100+ test methods.

import org.testng.Assert;
import org.testng.annotations.*;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.firefox.FirefoxDriver;

    WebDriver driver;

    @Parameters({"browser", "baseUrl"})
    @BeforeClass

        if (browser.equalsIgnoreCase("chrome")) {
            driver = new ChromeDriver();

            driver = new FirefoxDriver();

        System.out.println("URL: " + baseUrl);

    public void testLogin(String username, String password) {

        driver.findElement(By.id("pass")).sendKeys(password);
        driver.findElement(By.id("loginBtn")).click();

        Assert.assertTrue(title.contains("Dashboard"),
            "Login failed for user: " + username);

        System.out.println("✅ Login PASSED for: " + username);
    }

    @AfterClass
    public void tearDown() { driver.quit(); }
}

TestNG Data Providers — Data-Driven Testing

@DataProvider is TestNG's most powerful feature for data-driven testing. It runs the same @Test method multiple times with different datasets — testing login with 10 users, checkout with 5 card types, or search with 20 keywords using a single test method. It is the foundation of enterprise automation frameworks.

What is @DataProvider and Why is It Needed?

Without @DataProvider, testing multiple datasets requires duplicating test methods — a maintenance disaster:

// ❌ Without DataProvider — duplication nightmare
@Test
public void testLoginUser1() {
    login("admin@company.com", "Admin@123");
    // verify...
}
@Test
public void testLoginUser2() {
    login("manager@company.com", "Mgr@456");
    // same logic repeated!
}
@Test
public void testLoginUser3() {
    login("tester@company.com", "Test@789");
    // same logic repeated again!
}
// 50 users = 50 methods = unmaintainable!

Solution — @DataProvider + Object[][]

import org.testng.annotations.DataProvider;
import org.testng.annotations.Test;
import org.testng.Assert;

public class LoginDataDrivenTest {

    // Step 1: Define the data provider
    @DataProvider(name = "loginDataSet")
    public Object[][] getLoginData() {
        // Object[][] — each row = one test run
        // Each column = one parameter
        return new Object[][] {
            // {username,        password,   expectedResult}
            {"admin@co.com",    "Admin@123", true  },  // valid
            {"manager@co.com",  "Mgr@456",   true  },  // valid
            {"tester@co.com",   "Test@789",  true  },  // valid
            {"unknown@co.com",  "Wrong@999", false },  // invalid
            {"",                "",          false }   // empty
        };
    }

    // Step 2: Use the data provider in @Test
    @Test(dataProvider = "loginDataSet")
    public void testLogin(String user, String pass,
                          boolean expectedSuccess) {
        driver.get("https://app.company.com/login");
        driver.findElement(By.id("user")).sendKeys(user);
        driver.findElement(By.id("pass")).sendKeys(pass);
        driver.findElement(By.id("btn")).click();

        boolean loginSuccess = driver.getTitle()
                                     .contains("Dashboard");

        Assert.assertEquals(loginSuccess, expectedSuccess,
            "Login result mismatch for: " + user);

        System.out.printf(
            "User: %-25s | Expected: %-5s | Result: %s%n",
            user, expectedSuccess, loginSuccess);
    }
}

TestNG Reporter Log — Inline Test Step Logging

Reporter.log() is TestNG's built-in logging mechanism that writes custom messages directly into the TestNG HTML report. Unlike System.out.println() which only appears in the console, Reporter logs are preserved in the emailable-report.html — making them visible to project managers, clients, and CI/CD dashboards without IDE access.

Why Reporter.log()? The Problem with System.out

System.out.println() Problems:
• Only visible in the IDE console — disappears after run
• Not included in TestNG HTML reports
• Useless in headless CI/CD builds (Jenkins logs are ephemeral)
• Cannot be shared with non-technical stakeholders
Reporter.log() Advantages:
• Embedded permanently in emailable-report.html
• Visible in index.html under "Reporter Output" tab
• Survives CI/CD — Jenkins archives the HTML report
• Stakeholders see step-by-step test narrative

4 Overloaded Reporter.log() Methods

Method Description
Reporter.log(String s) Log to report only
Reporter.log(String s, boolean logToStdOut) Log to report + optionally to console
Reporter.log(String s, int level) Log with verbosity level (0=always, 1=verbose)
Reporter.log(String s, int level, boolean logToStdOut) Level + stdout control

import com.aventstack.extentreports.*;
import com.aventstack.extentreports.reporter.*;
import org.testng.ITestResult;
import org.testng.annotations.*;

public class ExtentReportBaseTest {

    // One instance per suite
    protected static ExtentReports extent;
    // One test per @Test method (ThreadLocal for parallel)
    protected static ThreadLocal<ExtentTest> test =
        new ThreadLocal<>();

    @BeforeSuite
    public static void initReport() {
        // Setup HTML reporter — output file path
        ExtentSparkReporter spark = new ExtentSparkReporter(
            "test-output/ExtentReport.html");
        spark.config().setDocumentTitle("QA Automation Report");
        spark.config().setReportName("Regression Suite");

        extent = new ExtentReports();
        extent.attachReporter(spark);
        // Add system info to report
        extent.setSystemInfo("Application", "MyBankApp");
        extent.setSystemInfo("Environment", "UAT");
        extent.setSystemInfo("Tester", "QA Team");
    }

    @BeforeMethod
    public void startTest(java.lang.reflect.Method method) {
        // Create test node for each @Test method
        ExtentTest extTest = extent.createTest(
            method.getName());
        test.set(extTest);
    }

    @AfterMethod
    public void endTest(ITestResult result) {
        if (result.getStatus() == ITestResult.FAILURE) {
            test.get().fail(result.getThrowable());
            // Capture screenshot on failure
            String screenshot = takeScreenshot(result.getName());
            test.get().addScreenCaptureFromPath(screenshot);
        } else if (result.getStatus() == ITestResult.SUCCESS) {
            test.get().pass("Test Passed ✅");
        } else {
            test.get().skip("Test Skipped ⚠️");
        }
    }

    @AfterSuite
    public static void flushReport() {
        extent.flush(); // Write report to disk
        System.out.println("→ Report: test-output/ExtentReport.html");
    }
}

TestNG Cross Browser Testing — Strategy & Setup

Cross Browser Testing ensures that a web application works correctly and consistently across different browsers (Chrome, Firefox, Edge, Safari). In enterprise environments, users access applications from varied browsers — a UI bug in Firefox missed in Chrome testing can cause critical production issues. TestNG's @Parameters combined with testng.xml makes this seamless.

Why Cross Browser Testing is Non-Negotiable

Real-World Problem: A banking web app's date-picker worked perfectly in Chrome but was completely invisible in Firefox due to a CSS z-index bug. Discovered only when customers complained — after PROD release.
Browser Market Share (2026):
Chrome: ~65% · Edge: ~13% · Firefox: ~7% · Safari: ~9%
Enterprise apps must support at minimum Chrome + Firefox + Edge.
TestNG Cross Browser Strategy:
1. Define browser as a @Parameter in testng.xml
2. Create a browser factory (switch/if-else on browser name)
3. Define multiple <test> blocks (one per browser) in testng.xml
4. Run in parallel for speed: parallel="tests" thread-count="3"

Browser Factory Pattern — Enterprise BaseTest Class

import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.firefox.FirefoxDriver;
import org.openqa.selenium.edge.EdgeDriver;
import org.openqa.selenium.chrome.ChromeOptions;
import org.openqa.selenium.firefox.FirefoxOptions;
import org.testng.annotations.*;

public class BaseTest {

    // ThreadLocal ensures each parallel thread
    // gets its OWN WebDriver instance — no conflicts!
    protected static ThreadLocal<WebDriver> driver =
        new ThreadLocal<>();

    @Parameters("browser")
    @BeforeClass
    public void setUp(String browser) {
        WebDriver webDriver;

        switch (browser.toLowerCase()) {
            case "chrome":
                ChromeOptions chromeOpts = new ChromeOptions();
                // chromeOpts.addArguments("--headless=new");
                webDriver = new ChromeDriver(chromeOpts);
                break;

            case "firefox":
                FirefoxOptions ffOpts = new FirefoxOptions();
                webDriver = new FirefoxDriver(ffOpts);
                break;

            case "edge":
                webDriver = new EdgeDriver();
                break;

            default:
                throw new IllegalArgumentException(
                    "Browser not supported: " + browser);
        }

        webDriver.manage().window().maximize();
        driver.set(webDriver); // Store in ThreadLocal
        System.out.println("✅ Browser started: " + browser
            + " | Thread: " + Thread.currentThread().getId());
    }

    // Helper to get driver for current thread
    public WebDriver getDriver() {
        return driver.get();
    }

    @AfterClass
    public void tearDown() {
        if (driver.get() != null) {
            driver.get().quit();
            driver.remove(); // Clean ThreadLocal
        }
    }
}

Topic-by-Topic Quick Reference

TestNG Asserts (Hard):
Assert.assertEquals(actual, expected, "msg")
Stops test at first failure. Use for critical flow steps.
Soft Assertions:
SoftAssert sa = new SoftAssert();
sa.assertEquals(...); sa.assertAll();
Collects ALL failures. Use for UI form field validation.
Test Priority:
@Test(priority = 1) — lower runs first. Default = 0.
Negative values allowed. Enforces business workflow order.
Parameters:
@Parameters({"browser"}) + <parameter name="browser" value="chrome"/>
Inject config values from testng.xml. One run per parameter set.
DataProvider:
@DataProvider(name="x") Object[][] + @Test(dataProvider="x")
Runs test once per data row. Data-driven testing powerhouse.
Reporter Log:
Reporter.log("Step message", true);
Embedded in emailable-report.html. Survives CI/CD builds.
Reports:
test-output/emailable-report.html + index.html auto-generated.
ExtentReports for professional dashboards with screenshots.
Cross Browser Testing:
ThreadLocal<WebDriver> + @Parameters("browser") + parallel testng.xml.
Always use ThreadLocal for parallel browser isolation.

SDET Interview Questions — Day 10 Topics

Q1: What is the difference between Hard Assert and Soft Assert?
A: Hard Assert stops the test at first failure. Soft Assert collects all failures and reports via assertAll() at the end.
Q2: What is the default execution order of TestNG @Test methods?
A: Alphabetical order by method name. Use priority attribute to control order.
Q3: What is the difference between @Parameters and @DataProvider?
A: @Parameters reads from testng.xml, runs test once. @DataProvider returns Object[][], runs test once per row — ideal for data-driven testing.
Q4: Where does Reporter.log() output appear?
A: In the TestNG emailable-report.html under Reporter Output, and optionally in console if logToStdOut=true.
Q5: Why use ThreadLocal<WebDriver> for cross-browser testing?
A: In parallel execution, each thread needs its own WebDriver instance. ThreadLocal isolates the driver per thread, preventing race conditions.
Q6: What files are auto-generated in test-output after TestNG run?
A: emailable-report.html (summary), index.html (detailed interactive), testng-results.xml (CI/CD integration).
Q7: How do you run cross-browser tests in parallel with TestNG?
A: In testng.xml, set parallel="tests" thread-count="3" and define separate <test> blocks with browser parameter for each browser.
